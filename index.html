Microsoft Entra 多要素認証を強制したい → Conditional Access（条件付きアクセス） 頻出！
  • 「誰が・どのアプリに・どの条件で」アクセスするかを制御するポリシーエンジン。
  • MFA要求・準拠デバイス要件・特定IPブロックなどを組み合わせられる。
  • 条件：ユーザー/グループ・クラウドアプリ・名前付きの場所（Named Location）・デバイスプラットフォーム・クライアントアプリ（レガシー認証の一括ブロックを含む）。
  • 制御：ブロック、MFA要求、準拠デバイス要求、利用規約（Terms of Use）への同意、セッション制御（サインイン頻度短縮・永続ブラウザーセッション無効化）。
  • Microsoft Entra ID P1 以上が必要。
⚠ セキュリティデフォルト（無料）と混同しない。カスタムポリシーが必要なら必ずConditional Access。
サインイン時の異常や漏えい資格情報を検知して自動対応したい → Identity Protection（サインインリスク・ユーザーリスクポリシー） 頻出！
  • Microsoft Entra ID P2が必要。Conditional Access内のリスク条件として構成する。
  • サインインリスク：その場のサインイン試行の異常度（不審な場所・匿名IP等）を評価 → ブロックまたはMFA要求。
  • ユーザーリスク：アカウント自体の漏えい可能性（漏えい資格情報の一致等）を評価 → 「高」リスク時にパスワード変更を必須にする。
その場限りの怪しいサインインを止めたい → サインインリスクポリシー
アカウント自体が漏えいしている疑い → ユーザーリスクポリシー（パスワード変更必須）
⚠ サービスアカウント等は除外設定し、リスク検出結果はLog Analytics/Sentinelへ転送して監視するのが定石。
特に重要な操作にフィッシング耐性のある強い認証を要求したい → Conditional Access の認証強度（Authentication Strength）
  • 組み込みの強度：MFA／パスワードレスMFA／フィッシング耐性MFA（FIDO2セキュリティキー、証明書ベース認証、Windows Hello for Business）。
  • 単に「MFAを要求」するより、許容する認証方法の組み合わせを細かく指定できる。
アプリがAzureリソースにアクセスする（パスワード不要） → マネージドID（Managed Identity） 頻出！
  • システム割り当て：リソースに1対1で紐付く。リソース削除で自動削除。
  • ユーザー割り当て：複数リソースで共有可能。ライフサイクルを独立管理。
  • 同じ権限を多数のリソースに与えるだけなら、ユーザー割り当てMIを1つ作成して使い回すのが最も効率的。環境（dev/test/prod）ごとに分離したい場合はテンプレートで環境別に事前作成し、リソースIDを参照する。
アプリのキー/パスワード管理が不要になる → Key Vaultとセットで語られることが多い。
GitHub Actions / AKS等、Azure外のワークロードからシークレットなしでAzureにアクセスさせたい → ワークロードIDフェデレーション（Workload Identity Federation） 頻出！
  • アプリ登録（またはユーザー割り当てMI）にフェデレーション資格情報を構成し、外部IdPが発行するOIDCトークンを信頼する。
  • シークレット・証明書の管理が不要。GitHub Actions、他クラウドのワークロード、AKSのサービスアカウントなどが対象。
  • AKSでは「Microsoft Entraワークロード ID」を有効にし、Kubernetesサービスアカウントとフェデレーション資格情報を構成する。
最小権限でAzureリソースへのアクセスを管理したい → Azure RBAC（ロールベースアクセス制御） 頻出！
  • スコープ：管理グループ ＞ サブスクリプション ＞ リソースグループ ＞ リソース
  • Owner / Contributor / Reader が代表的な組み込みロール。
  • カスタムロールも作成可能（JSON定義）。Actions（管理操作）とDataActions（データ操作。例：BLOBの読み取り）を区別し、特定操作だけ除外したいときはNotActions/NotDataActionsを使う。
  • 継承は上位スコープ→下位スコープの一方向のみ。下位で付与したロールが上位に影響することはない。
RBAC vs Microsoft Entra ロール
RBAC = Azureリソース（VM・ストレージ等）への権限管理
Microsoft Entra ロール = Microsoft Entra ID自体（ユーザー・グループ管理等）への権限管理
⚠ BLOBデータの読み取り等の「データプレーン操作」は、Reader/Contributorのような管理プレーンロールでは許可されない。Storage Blob Data ReaderのようなDataActionsを含むロールが必要。
アプリ登録とサービスプリンシパル、SSO方式（SAML/OIDC）の使い分けが分からない → アプリ登録＝アプリの定義、サービスプリンシパル＝テナント内での実体・権限付与単位
  • アプリ登録（App Registration）：アプリのグローバルな定義（マルチテナント含む）。作成すると自テナントにサービスプリンシパルが自動生成される。
  • エンタープライズアプリケーション：他テナント/ギャラリーのアプリを自テナントで使うためのサービスプリンシパル（＝そのテナントでの利用インスタンス）。RBACやアクセス割り当てはサービスプリンシパル単位で行う。
  • SSO方式の選択：SAMLは既存のエンタープライズ標準・SAML専用SaaS向け、OIDC（OpenID Connect、OAuth 2.0ベース）はモダンなWeb/モバイル/SPAアプリ向けで新規開発では基本こちらを選ぶ。
外部ユーザー（取引先など）にMicrosoft Entra IDのアプリへアクセスさせたい → Microsoft Entra B2Bコラボレーション
  • 招待されたゲストユーザーが自社のMicrosoft Entra IDテナントにアクセス。
  • B2C（一般消費者向けID管理）と混同しない。
B2B vs B2C
B2B = 企業間コラボ（パートナー、取引先）
B2C = エンドユーザー向けアプリのID管理（Googleログイン等のソーシャルID連携）
⚠ Azure AD B2Cは2025年5月1日以降新規購入不可（既存テナントは2030年5月まで利用継続可）。Microsoft Entra External IDはB2Cの単純な改称ではなく別製品の後継で、消費者向けアプリのセルフサービスサインアップ/サインインを新規実装する場合はこちらを使う。
社外パートナーや監査法人に、期限付き・承認制でアプリ/グループへのアクセスを付与したい → 資格管理（Entitlement Management）のアクセスパッケージ 頻出！
  • アプリ・グループ・SharePointサイト等をまとめた「アクセスパッケージ」を作成し、承認フロー・有効期限・定期アクセスレビューを設定できる。
  • 接続済み組織（Connected Organization）を登録すると、Entra ID未導入の外部組織のユーザーもリクエスト対象にできる。
  • B2Bゲスト招待を都度手動で行うより、大規模・自動化されたガバナンスに向く。
  • ライフサイクルワークフロー（Lifecycle Workflows）：入社（Joiner）・異動（Mover）・退職（Leaver）のタイミングに合わせて、アクセスパッケージの自動割り当て・グループ追加・アカウント無効化などを自動実行できる。
Microsoft Entra ID Governance または Microsoft Entra Suite が必要（アクセスパッケージ等の一部機能はP2でも動作する場合がある）。
オンプレミスADのIDをEntra IDと同期したい → Microsoft Entra Connect Sync／Cloud Sync
  • パスワードハッシュ同期（PHS）：最もシンプル。シームレスSSOと組み合わせるとオンプレ資格情報でSSOできる。
  • パススルー認証（PTA）：オンプレ側エージェントでパスワードを検証。ハッシュはクラウドに送らない。
  • フェデレーション（AD FS等）：既存の外部IdPをそのまま使いたい場合。
  • Cloud Sync：軽量プロビジョニングエージェント。買収などで互いに信頼関係のない複数のオンプレADフォレストを1つのテナントに同期する場合に有利。
同期・認証方式の選び方
オンプレAD障害時もクラウド側だけでサインインを継続したい → PHS（パスワードハッシュ同期）
パスワードハッシュを一切クラウドに送りたくない → PTA（パススルー認証）
既存のスマートカード認証やサードパーティIdPをそのまま使いたい → フェデレーション（AD FS等）
相互信頼のない複数フォレストを軽量にまとめたい → Cloud Sync
⚠ PHSはオンプレAD DSがダウンしていてもEntra ID側の認証が継続できる点がPTA/フェデレーションとの最大の違い。
ユーザー自身にパスワードをリセットさせ、オンプレADにも反映したい → SSPR（セルフサービスパスワードリセット）＋ パスワード書き戻し
  • SSPRはP1以上で有効化（一部機能はFreeでも可）。ハイブリッド環境ではEntra Connectでパスワードライトバックを有効にしてオンプレADにも反映させる。
レガシーなLDAP/Kerberos/NTLM依存アプリや、オンプレADファイル共有をAzure上で運用したい → Microsoft Entra Domain Services／アプリケーションプロキシ／Azure Files Entra Kerberos認証 頻出！
  • Microsoft Entra Domain Services：Entra IDをソースにマネージドのドメインサービス（LDAP/Kerberos/NTLM/グループポリシー相当）を提供。レガシーなオンプレADベースアプリをリフト＆シフトでAzureに移行する際に、ドメインコントローラーを自前運用せずに済む。
  • Microsoft Entra アプリケーションプロキシ：オンプレミスのWebアプリを外部エージェント経由でEntra IDのConditional Access等を適用しつつ安全に社外公開する（VPN不要）。
  • Azure Files：Entra Kerberos認証（クラウドネイティブ、Entra IDのユーザー/グループでSMBアクセス制御）と、オンプレAD DS認証（既存ADドメイン参加PCからのシームレスアクセス、AD DSへのライン・オブ・サイトが必要）を要件に応じて使い分ける。
ガバナンス
全サブスクリプションに一律ルールを強制したい（例：特定リージョンのみ許可） → Azure Policy 頻出！
  • 準拠していないリソースを検出・拒否・自動修復できる。
  • 管理グループに割り当てて組織全体に適用するのが典型パターン。
  • イニシアチブ（Initiative）＝複数ポリシーをまとめたセット。
  • 親スコープのポリシーから特定サブスクリプション/リソースだけ除外したい → ポリシー例外（Exemption）を使う（ポリシー自体を作り直す必要はない）。
  • 一時的にポリシーの拒否評価を止めたい → 割り当ての強制モード（Enforcement mode）をDoNotEnforceにする（コンプライアンス評価・ログは継続するが拒否は行わない）。
Azure Policy の効果（Effect）比較
Deny
動作作成/更新を拒否
Append
動作作成時にフィールド追加
Modify
動作既存リソースも更新可
Audit
動作非準拠を記録のみ
AuditIfNotExists
動作関連リソース欠如を監査
DeployIfNotExists
動作欠如していれば自動デプロイ
DenyAction
動作リソースの削除操作自体を拒否
⚠ Append/Modifyは「作成をブロックせず値を強制」、DeployIfNotExists/AuditIfNotExistsは「関連リソース（診断設定等）の有無」をチェックする点で対象が異なる。DeployIfNotExistsの実行にはマネージドIDが必要。DenyActionは既存リソースの削除操作をブロックする効果で誤削除防止に有効。効果に優劣はなく用途で選ぶ（評価順は disabled → append/modify → deny → audit → manual → auditIfNotExists → denyAction）。RBACと混同注意：RBACは「誰が何をできるか」、Policyは「何を作れるか」のルール。
タグ付けルールを組織全体で強制・継承したい → Azure Policy（Deny/Append/Modify）でタグ付けを強制
  • 必須タグが未設定のリソース作成を止めたい → Deny効果でブロック。
  • 作成時にタグを自動付与したいだけ → Append効果。既存リソースにも遡って追加/補正したい → Modify効果（remediation taskで既存分に適用）。
  • 組み込みポリシー定義でリソースグループのタグをリソースへ自動継承させることも可能。
  • 1リソースに付与できるタグは最大50個。
複数サブスクリプションを階層管理したい → 管理グループ（Management Groups） 頻出！
  • ルート管理グループ配下に最大6階層（ルート管理グループ・サブスクリプション自体はこの階層数に含まない）。
  • Azure Policy・RBAC を管理グループに割り当てると配下のサブスクリプションに継承される。
  • 大企業の組織構造（部門別サブスク）をそのまま反映できる。
  • Landing Zone設計の定石：ルート直下の中間管理グループ（プラットフォーム/ランディングゾーン等）に共通イニシアチブを1回割り当て、配下の環境別管理グループやサンドボックスにはポリシー例外で個別調整する。
オンプレミスや他クラウドのサーバーにもAzure Policy・Monitor・Defender for Cloudを適用したい → Azure Arc
  • オンプレミス/他クラウド（AWS・GCP等）のサーバーをAzure Resource Manager上の「Arc対応サーバー」として登録し、Azureネイティブのリソースと同様に管理できるようにする。
  • 登録後はAzure Policyの割り当て、Azure Monitor（AMA/DCR）によるログ収集、Defender for Cloudによる保護など、Azureと同じガバナンス/監視の仕組みをそのまま適用できる。
  • Arc対応Kubernetes、Arc対応SQL Serverなど、サーバー以外のワークロードにも対応。
リソースの誤削除・誤変更を防ぎたい → リソースロック（Resource Locks）
  • CanNotDelete：削除不可・変更は可。
  • ReadOnly：削除・変更ともに不可（= 読み取り専用）。
  • 所有者でもロック解除しなければ削除できない。
コストタグ付け・リソースのグループ化・テンプレートデプロイを一括管理したい → Azure Blueprints / Landing Zone
  • Blueprints = Policy・RBAC・ARMテンプレートを1パッケージにして繰り返しデプロイ。
  • Landing Zone = 大規模組織向けの推奨アーキテクチャパターン（CAF準拠）。
⚠ Azure Blueprintsは2026年7月31日に段階的リタイア開始、2027年1月31日に完全リタイア予定。リタイア後は既存Blueprintの拒否割り当て（Blueprint Locks）も削除される。新規案件ではテンプレート仕様（Template Specs）＋デプロイスタック（Deployment Stacks）の組み合わせが推奨される。
テンプレートでデプロイした一式のリソースを、誰であっても削除・変更できないよう一括ロックしたい → デプロイスタック（Deployment Stacks）＋ denySettings
  • 複数リソースをまとめて1つの「スタック」として管理し、denySettingsで削除・変更操作をスタック単位で拒否できる。
  • 個々のリソースに1つずつロックを設定する手間を省ける。ARM/Bicepデプロイと統合されている。

コスト・マルチテナント管理
コストが予算を超えそうなときに複数段階で通知したい → Cost Management の予算（Budget）＋ アクショングループ
  • 予算に複数のしきい値（例：50%/80%/100%）を設定し、超過時にメール通知やアクショングループ（Webhook/Functions等）を呼び出せる。
リソースのタグは変更せず、コストレポート上だけ親スコープのタグを継承させたい → Cost Management の「タグ継承（Tag Inheritance）」
  • サブスクリプション/管理グループのタグをコストデータに仮想的に適用する機能。実リソースのタグ自体は書き換えない。
安定稼働するVM/DB等のコストを長期契約で削減したい → Azure予約（Reservations）
  • 1年/3年の予約でオンデマンド比最大72%割引。スコープを「共有」にすると組織内の複数サブスクリプションで消費可能。
  • インスタンスサイズの柔軟性が有効なVMシリーズなら、同一シリーズ内でサイズを変更しても割引が引き継がれる。
  • Azure Hybrid Benefit：Windows Server/SQL Serverの既存オンプレライセンス（Software Assurance付き）をAzure側の課金に持ち込んで二重支払いを避ける。予約/Savings Planと併用可能。
  • Dev/Test価格：本番以外のサブスクリプションに適用できる割引レート（一部サービスの月額ライセンス費用が不要になる等）。本番ワークロードには使えない。
  • Spot VM：Azure側の余剰キャパシティを大幅割引で利用。いつでも立ち退き（Eviction）される前提のため、バッチ処理やステートレスな中断可能ワークロード向け。

MSP/パートナーとして複数の顧客テナントのリソースを自社から一元管理したい → Azure Lighthouse
  • 顧客テナントのサブスクリプション/リソースグループへのアクセスを自社（管理側）テナントに委任し、テナントを跨いでまとめて運用・監視できる。
  • 顧客側はRBACロールの委任を許可するだけでよく、自社ユーザーを顧客テナントに個別作成する必要がない。
監視・セキュリティ
全リソースのログ・メトリクスを一元監視したい → Azure Monitor 頻出！
  • メトリクス（数値）＋ログ（Log Analytics）の両方を扱う統合監視サービス。
  • アラート → アクショングループ（メール/SMS/Webhook/Function/Automationランブック呼び出しなど）で自動対応。

ストレージ（Blob・File・Queue・Table）
大量の非構造化データ（画像・動画・バックアップ）を安価に保存したい → Azure Blob Storage 頻出！
  • アクセス層：Hot（頻繁アクセス）/ Cool / Cold / Archive（取り出しに時間がかかる）。
  • ライフサイクル管理ポリシーで自動的に層を移動・削除できる。
  • 不変ストレージ（WORM）：法規制対応・改ざん防止。設定方法はコンテナー（またはBLOBバージョン）に対する不変性ポリシーを作成する（SASの「stored access policy」とは別概念なので混同注意）。
  • 不変性ポリシーの種類：期間ベース保持ポリシー（指定期間は変更・削除不可、新規書き込みは可）／ 訴訟ホールド（期間指定なしで保持）。
  • Data Lake Storage Gen2：Blob + 階層型名前空間（HNS、ビッグデータ分析向け）。詳細は下記ADLS Gen2カード参照。

ビッグデータ分析基盤としてHadoop互換のファイルシステムが必要 → Azure Data Lake Storage（ADLS）Gen2
  • Blob Storage上に階層型名前空間（HNS）を有効化した構成。ファイルシステム互換（ディレクトリのリネーム/削除がアトミック）でビッグデータ分析に最適化。
  • POSIX ACL：ディレクトリ/ファイル単位でユーザー・グループ・その他に対するread/write/executeを細かく設定可能。RBACはコンテナー単位までしか制御できないため併用が前提。
  • Synapse Analytics・Databricks・HDInsight・Microsoft Fabric（OneLake）など分析エンジンとのネイティブ連携が可能。ビッグデータ分析基盤の既定のストレージ層として使われる。
  • Blob用のツール・APIとも互換性があり、既存のBlobベースのワークロードから段階的に移行できる。
「Hadoop/Spark分析基盤のストレージ」「ディレクトリ単位のACLで権限制御したい」→ ADLS Gen2（HNS有効化）。単純なオブジェクト保存だけならHNS無効の通常Blobで十分。

Blobの誤削除・誤上書きから復旧できるようにしたい → Blobバージョニング ＋ 論理削除（Soft Delete） 頻出！
  • Blobバージョニング：上書き・削除のたびに自動で旧バージョンを保持。任意のバージョンに復元可能。
  • 論理削除（Soft Delete）：削除後も保持期間内はごみ箱のように復元可能（コンテナー単位・Blob単位の両方に設定可）。
  • 誤操作対策の頻出パターンは「バージョニング＋論理削除」の組み合わせで問われる。
  • コンテナーの論理削除：コンテナー自体の誤削除からも復旧可能（Blob単位の論理削除とは別に有効化が必要）。
  • ポイントインタイムリストア（PITR）：コンテナー単位で過去の任意時点の状態にBlobをロールバック可能。バージョニング＋変更フィード＋論理削除が有効なことが前提条件。
  • オブジェクトレプリケーション：コンテナー単位で別のストレージアカウント（別リージョンも可）へ非同期に自動コピーする機能。アプリから読み取り可能なレプリカを作る用途やリージョン間のデータ移動に使う（GRSの災害対策用の裏側コピーとは別物で、直接読み書きできない点が異なる）。
  • 静的Webサイトホスティング：$webコンテナーを有効化するとBlob Storageだけでサーバーレスに静的サイト（HTML/CSS/JS）を配信できる。
ストレージアカウントの種類・パフォーマンス層を選びたい → ワークロードの形とアクセスパターンで選ぶ
  • StorageV2（汎用v2）：Blob/Files/Queue/Tableをすべて扱える標準アカウント。Hot/Cool/Cold/Archive層を利用可能。特別な理由がなければこれを選ぶ。
  • Premium Block Blob：SSDベース。低レイテンシ・高トランザクションレートが必要なワークロード（分析・IoTデータ取り込み等）向け。アクセス層の概念はなし。
  • Premium Page Blob：非マネージドディスク（VHD）向けのSSDベース高性能ストレージ。
  • Premium File Storage（FileStorage）：Azure Files Premiumティア専用のSSDベースアカウント。
「高トランザクション・低レイテンシのBlobワークロード」→ Premium Block Blob。「Azure FilesでNFS 4.1やPremium SMBが必要」→ FileStorageアカウント。
SMB/NFSのファイル共有をクラウドで使いたい（オンプレのファイルサーバー移行） → Azure Files 頻出！
  • SMB 3.1.1（既定・暗号化）/ 3.0 / 2.1 対応。NFS 4.1にも対応。Windowsドライブとしてマウント可能。
  • Azure File Sync：オンプレのファイルサーバーとクラウドをリアルタイム同期。キャッシュ機能付き。
  • Premium（SSD）/ Standard（HDD）の2ティア。NFS 4.1共有はPremiumティアでのみ利用可能（Standardでは不可）。
「オンプレのファイルサーバーをクラウド化したい」→ Azure Files + File Sync が鉄板。
Azure Filesをユーザー単位のNTFS権限でSMB認証（Kerberos）したい → 識別ベース認証：オンプレAD DS ／ Microsoft Entra Kerberos ／ Microsoft Entra Domain Services から選択 頻出！
  • オンプレAD DS認証：オンプレADのアカウントとAzure ADを同期させ、既存のオンプレADユーザー資格情報でKerberos認証。オンプレADへのライン・オブ・サイトが必要。
  • Microsoft Entra Kerberos：Microsoft Entra Connectで同期されたハイブリッドIDアカウントに対し、クラウド側だけでKerberosチケットを発行。オンプレADへの継続的な接続が不要。
  • Microsoft Entra Domain Services：マネージドドメインを使い、オンプレADを持たない（または持ちたくない）環境でAD互換のKerberos認証を実現。オンプレADからのリフト＆シフト移行で、オンプレAD運用を維持したくない場合に選ぶ。
  • Microsoft Entra ID認証：現状SMBマウントには非対応。REST API（OAuth）経由のアクセスのみ。
  • いずれの方式でも、共有レベルのRBAC（Azure組み込みロール）と、ディレクトリ/ファイル単位のNTFS ACLの両方を構成する必要がある。
「オンプレADは維持しつつAzureでシームレスに認証」→ AD DS認証。「オンプレAD管理を減らしクラウド完結にしたい」→ Entra Kerberos。「オンプレADが無い／持ちたくないがAD互換認証が必要」→ Entra Domain Services。
SAP HANAなど超高IOPS・低レイテンシが必要なエンタープライズファイルストレージが必要 → Azure NetApp Files
  • NetApp社の技術基盤をAzure内に統合したエンタープライズ向けファイルストレージ。NFSv3/v4.1・SMB・デュアルプロトコルに対応。
  • Azure Filesより高いIOPS・低レイテンシが求められる基幹業務（SAP HANA、HPC、大規模DBワークロード）向け。SAP HANA認定ストレージ。
  • サービスレベル：Standard / Premium / Ultra（スループット段階）。容量プール単位でプロビジョニングする。
「Azure Filesでは性能不足」「SAP HANA向け認定ストレージ」→ Azure NetApp Files。
アプリ間のメッセージキューが必要（簡易・大量） → Azure Queue Storage（簡易） / Azure Service Bus（高機能）
Queue Storage vs Service Bus
Queue Storage = シンプル・大量メッセージ（メッセージ最大64KiB、単一キュー上限は500TiB）
Service Bus = 順序保証・重複排除・セッション・Dead Letter Queue（DLQ）など高機能
「メッセージの順序保証が必要」「64KBを超えたい」→ Service Bus を選ぶ（Standardは256KB、Premiumは100MBまで対応）。
シンプルなキー値ストアを低コストで使いたい → Azure Table Storage
  • NoSQLのキー値ストア。パーティションキー＋行キーの複合キーでエンティティを一意に識別。スキーマレス。
  • Cosmos DB for Table APIと互換性のあるデータモデル・SDKを使用（アプリコードを変更せずに移行可能）。
  • 低コストだが、グローバル分散・低レイテンシSLA・複数の整合性レベルなどCosmos DBの高度な機能は持たない。
Table Storage vs Cosmos DB for Table
Table Storage = 単一リージョン・低コスト・シンプルなキー値アクセスで十分な場合
Cosmos DB for Table = グローバル分散・自動インデックス・保証された低レイテンシSLA・高スループットが必要な場合
「とにかく安く」「単一リージョンで十分」→ Table Storage。「グローバル分散・SLA保証・自動スケール」→ Cosmos DB for Table。

Azure Migrateでオンプレミス VM（VMware/Hyper-V）をAzureへ移行する手順 → 探索 → アセスメント → レプリケーション → 移行（カットオーバー） 頻出！
  1. Azure Migrateプロジェクトを作成し、「探索とアセスメント」ツール（Azure Migrate: Discovery and assessment）を追加する。
  2. ポータルから移行アプライアンス（OVAテンプレート等）をダウンロードし、オンプレミスの仮想化基盤（vCenter配下など）にデプロイする。
  3. アプライアンスの構成用URLを開き、プロジェクトキーで登録し、vCenter/Hyper-Vホストへの接続情報を入力する。
  4. アプライアンスが対象VM群を継続的に探索し、パフォーマンスデータを収集する。
  5. 収集データをもとにアセスメント（Azure推奨サイズ・月額コスト見積り・互換性チェック）を実行する。
  6. 「サーバー移行」ツール（Azure Migrate: Server Migration）を追加し、対象VMのレプリケーションを有効化する（初回フルレプリケーション後、継続的な差分同期）。
  7. 隔離されたネットワークでテスト移行を実施し、起動・動作を検証する。
  8. 準備が整ったらカットオーバー（移行）を実行。最終差分同期後にレプリケーションを終了し、Azure VMとして起動する。
VMwareはエージェントレス（アプライアンスが探索・レプリケーションを代行）。Hyper-V／物理サーバーは対象VM内にMobility Serviceエージェントをインストールするエージェントベースの構成になる点に注意（試験ではこの違いが問われやすい）。
Azure Data Factoryでデータ移行／ETLパイプラインを構築する手順 → リンクサービス → （統合ランタイム）→ データセット → パイプライン → トリガー 頻出！
  1. Data Factoryインスタンスを作成する。
  2. リンクサービス（Linked Service）を作成し、ソース／シンクへの接続情報（認証情報を含む）を定義する。
  3. オンプレミスのデータストアに接続する場合、対象サーバーにセルフホステッド統合ランタイム（Self-hosted IR）をインストールし、Data Factoryに登録する。
  4. データセット（Dataset）を作成し、リンクサービス上の具体的なデータ構造（テーブル・ファイルパス等）を指定する。
  5. パイプラインを作成し、Copyアクティビティ（単純コピー）またはMapping Data Flow（変換を伴うETL）を追加する。
  6. トリガー（スケジュール実行・イベントベース・手動）を設定し、パイプラインを実行する。
  7. 「監視」タブでパイプラインの実行状況・失敗の原因を確認する。
増分ロード（毎回全件でなく差分のみ取り込む）には、前回実行時のウォーターマーク値（最終更新日時等）をコントロールテーブルに保存し、Lookupアクティビティで取得 → Copyアクティビティでフィルタ → 実行後に最大値へ更新、という「ウォーターマーク方式」が定番パターン。
Database Migration Service（DMS）でオンプレミスDBをAzureへ移行する手順 → 移行プロジェクト作成 → 接続情報入力 → （継続）レプリケーション → カットオーバー 頻出！
  1. ソースDBに到達できるVNet内にDatabase Migration Serviceインスタンスを作成する。
  2. 移行プロジェクトを作成し、ソースDBの種類・ターゲットの種類・移行モード（オフライン／オンライン）を選択する。
  3. ソースDBサーバーへの接続情報（認証情報）を入力する。
  4. ターゲット（Azure SQL Database／Managed Instance／VM上のSQL Server等）への接続情報を入力する。
  5. 移行対象のデータベース・スキーマを選択する。
  6. （オンラインモードの場合）完全バックアップの復元後、継続的なレプリケーションによりトランザクションログを適用し続け、ソースとターゲットの差分を最小化する。
  7. 準備が整ったらアプリケーションを一時停止し、最終同期の完了を待ってカットオーバーを実行する。
  8. アプリケーションの接続文字列をターゲットに切り替える。
オフラインモードはダウンタイムが大きいがシンプル、オンラインモードは継続レプリケーションでダウンタイムを最小化できるが構成がやや複雑。SQL Server→Azure SQL MIの移行で対応バージョン（SQL Server 2016 SP3以降／2017／2019 CU20以降／2022）であれば、Managed Instance linkによる継続レプリケーションも選択肢になる。
暗号化・データ保護
用途に応じた暗号化・マスキング機能を使い分けたい → 保護したい対象で機能を選ぶ 頻出！
保護範囲比較（塗りつぶし＝守れる：保存時／転送中／DBAから／画面表示 の4軸）
TDE
（透過的データ暗号化）
保存データ全体（データファイル・ログ・バックアップ）を暗号化。SQL DB/MIで既定有効、アプリ変更不要
Always Encrypted
特定の機密列をクライアント側で暗号化・復号。DB管理者からも平文の値を秘匿できる唯一の方式
Dynamic Data
Masking（DDM）
クエリ結果の表示のみマスク。データ自体は平文のまま保存・伝送されるため暗号化の代替にはならない
  • インフラストラクチャ暗号化：ストレージの物理層で既定の暗号化にさらに重ねる二重暗号化。プラットフォーム管理鍵に加え二重防御が必要な規制要件向け。
  • カスタマーマネージドキー（CMK）：暗号化キーの管理主体をMicrosoftから顧客に移す。Key Vaultで顧客がキーをローテーション・失効管理。
⚠「DB管理者にも値を見せたくない」→ Always Encrypted。「画面表示だけ隠したい」→ DDM（マスキングは暗号化ではない）。「同じデータを2回暗号化する規制要件」→ インフラストラクチャ暗号化 + CMK。
通信経路（転送中）のデータを保護したい → セキュア転送の強制 ＋ TLS/SMB暗号化
  • ストレージアカウントの「セキュア転送が必須」設定：HTTP接続を拒否しHTTPS（TLS）のみ許可。既定で有効。
  • TLSの最小バージョンをアカウント単位で指定可能（TLS 1.2以上を推奨・強制）。
  • Azure Files：SMB 3.1.1は既定で暗号化。マウント時にSMB暗号化を強制することも可能。
  • Always Encrypted with secure enclaves：暗号化された列に対してもサーバー側のセキュアエンクレーブ内でパターンマッチングや範囲検索・JOINが可能（通常のAlways Encryptedは等価検索のみで範囲検索不可という制約を緩和）。
「暗号化列に対して範囲検索・LIKE検索をしたい」→ Always Encrypted with secure enclaves。通常のAlways Encryptedでは実現できない。

重要指標（必ず暗記）
RTO / RPO の定義 → RTO = 復旧時間目標　／　RPO = 復旧時点目標 頻出！
  • RTO（Recovery Time Objective）：障害発生からサービス復旧までの最大許容時間。
  • RPO（Recovery Point Objective）：障害発生時に許容できる最大データ損失時間。
判断の基準
RTO短い = サービス止められない → 自動フェールオーバー必須
RPO短い = データ損失NG → 同期レプリケーション or 高頻度バックアップ
「RTO=0, RPO=0」の要件 → Active-Active 構成（Azure Traffic Manager + 複数リージョン）。
RPO計算の具体例（最後の成功バックアップ〜障害発生までの実測）
前日 22:00 → 最後に成功したバックアップ
当日 14:00 → 障害発生（データ消失）
RPO = 14:00 − 前日22:00 = 約16時間（データ損失）
⚠ RPOは「バックアップの実行間隔（例: 1日1回）」そのものではない。実際のRPOは障害発生タイミング次第で0時間〜ほぼ間隔と同じ時間の範囲で変動する、実測ベースの値。ASRのような継続的レプリケーションはRPOを数分〜数十分まで短縮できる。
複合SLAの計算（暗記用）
直列構成（両方が正常でないとサービス継続できない）= 各コンポーネントSLAの単純乗算　例）99.95%×99.99%≈99.94%（単体より低下）
冗長構成（n個中1つでも生きていればよい）= 1 − (1 − A)ⁿ　例）99.9%が2台冗長 → 1−(1−0.999)²=99.9999%（単体より向上）

  • Azure Backup：誤削除・破損・ランサムウェアからのデータ保護が主目的。復元は新規作成寄りでRTOは長め。
  • Site Recovery（ASR）：VM／物理サーバー単位の継続レプリケーション＋リージョンフェールオーバーが主目的。RTO/RPOが短い。

⚠ 混同注意：Blobの「バージョニング＋ポイントインタイムリストア（運用バックアップ）」は同一アカウント内保持のため、アカウント削除・侵害には無力。「オブジェクトレプリケーション」はバックアップではなくレプリケーション（ソースでの削除・暗号化がターゲットに伝播しうる）。真のランサムウェア対策には vaulted バックアップが必要。

ディザスタリカバリ（DR）
VMやオンプレサーバーのDRを自動化したい → Azure Site Recovery（ASR） 頻出！
  • Azure → Azure / オンプレ → Azure のレプリケーションが可能。「Azure → オンプレ」は独立したレプリケーション方向ではなく、オンプレ→Azureへフェールオーバーした後のフェールバックとしてのみ発生する。
  • フェールオーバーテストを本番に影響なく実施できる（本番・オンプレと接続しない分離テスト用VNetを指定）。
  • RPO は数秒〜数分、RTOは数分〜数時間（ポリシー次第）。
  • リカバリプラン：複数VMをグループ化し、グループ単位で起動順序（ブートオーダー）を定義。Automationランブックのステップを前後に挿入して、DNS更新等も自動化できる。
  • Hyper-Vからのレプリケーションは System Center VMM 経由に加え、VMMなしでHyper-Vホストに直接Providerを登録する構成にも対応（小規模拠点向け）。
⚠ 「DB起動後にアプリ→Webの順で立ち上げたい」等の多層システムの起動順序制御 → リカバリプランが正解（レプリケーションポリシーの保持期間設定ではない）。
⚠ Azure Backup の geo リストアは別リージョンへの新規作成による復元のため数時間規模かかる。「RTO数十分以内」等の短いRTO要件には使えない → ASR かフェールオーバーグループ等の常時レプリケーション型を使う。
Azureのリージョンペアが自動的にやってくれること／やってくれないこと → ペアは"土台"にすぎない。DRは別途構成が必要
  • 自動で得られるのは「広域障害時にペアの一方が優先的に復旧される」「計画的なプラットフォームメンテナンスがペア間で時間差をつけて順番に展開される」の2点のみ。
  • VMの自動レプリケーション・自動フェールオーバーはされない（ASR等を別途構成）。
  • ストレージの冗長性（LRS→GRS等）も自動では切り替わらない（作成時・変更時に明示的な選択が必要）。
  • DNSの自動相互フェールオーバーも行われない（Traffic Manager / Front Door 等を別途構成）。
⚠「リージョンペア＝DR」ではない。ペアはMicrosoft運用上の性質にすぎず、実際のDRはSite Recovery・SQLフェールオーバーグループ・Traffic Manager/Front Doorなど具体的なサービスの組み合わせで実現する。
本番環境への影響を抑えつつ耐障害性を継続的に検証したい → Azure Chaos Studio

  • リージョン全体の切り替えを伴わない、粒度の細かいレジリエンス検証に向く。
⚠ ASRのテストフェールオーバーはリージョン単位の大掛かりなDR検証、Chaos Studioはゾーン障害・レイテンシ等の粒度の細かい障害注入検証、と使い分ける。負荷試験（Azure Load Testing）やアラート閾値の一時変更は障害注入の代替にはならない。

4つの自動スケール機能の違い
HPA（水平Pod自動スケーラー）
対象：Podの数
仕組み：CPU使用率など指定メトリクスに応じてPodレプリカ数を増減。「水平」＝同じ大きさのPodを横に増減
VPA（垂直Pod自動スケーラー）
対象：Pod1つのサイズ
仕組み：個々のPodのCPU/メモリのリクエスト・リミット値を自動調整。「垂直」＝Pod自体を大きく/小さく
Cluster Autoscaler
対象：Nodeの数
仕組み：Podをスケジュールできない（リソース不足）場合にNodeを追加。余剰Nodeは自動削除
Virtual Nodes
対象：バーストキャパシティ
仕組み：ACI（サーバーレスコンテナー）を仮想的なNodeとして連携。通常のNode追加より数秒単位で高速にバースト対応
HPAとCluster Autoscalerは連動して使われることが多い（HPAがPodを増やす→既存Nodeに乗り切らない→Cluster AutoscalerがNodeを追加）。KEDAはHPAを拡張し、CPU/メモリ以外の外部イベントソース（Service Busキューの滞留数など）をスケーリングのトリガーにできる仕組み。

大量のIoTデバイスとクラウド間の双方向通信・デバイス管理を行いたい → Azure IoT Hub（＋必要に応じてIoT Edge／IoT Central） 頻出！
  • Azure IoT Hub：IoTデバイス群とクラウドをつなぐ中央ハブ。デバイス→クラウドのテレメトリ受信だけでなく、クラウド→デバイスへのコマンド送信（双方向通信）や、デバイスごとの個別ID・認証情報の管理（デバイスレジストリ）が中心的な特徴。
  • デバイスツイン（Device Twins）：各デバイスの状態（構成・条件）をJSONで表現し、クラウド側が「望ましい状態（desired properties）」を書き込み、デバイス側が「実際の状態（reported properties）」を報告することで、非同期に状態を同期できる（デバイスがオフラインでも、次回接続時に反映される）。
  • ダイレクトメソッド（Direct Methods）：デバイスがオンラインの間に、クラウドから同期的にコマンドを呼び出し即時応答を受け取る仕組み（例：デバイスの再起動を今すぐ実行）。
  • Device Provisioning Service（DPS）：大量のデバイスを、手動登録なしに自動でIoT Hubへゼロタッチプロビジョニングする補助サービス。工場出荷時点でのデバイス大量展開に使う。
  • Azure IoT Edge：IoT Hubで管理するロジック（コンテナー化されたモジュール）を、クラウドではなくデバイス側（ゲートウェイ／エッジ機器）で実行する仕組み。ネットワーク接続が不安定・オフラインでもローカルで処理を継続でき、接続が回復した時点でクラウドと同期する。大量データをクラウドへ送る前にローカルでフィルタリング・集約し、帯域幅を節約する用途にも使う。
    • IoT Edgeランタイム：エッジデバイス上で動作する常駐ソフトウェア本体。edgeAgent（デプロイマニフェストに従ってモジュールの起動・停止・監視・再起動を担当）とedgeHub（モジュール間・モジュール⇔クラウド間のメッセージルーティングを担当）という2つの標準モジュールで構成される。
    • IoT EdgeデバイスはIoT Hubに接続された特殊な種類のデバイスとして登録・管理される。IoT Edgeランタイムは、IoT Hub側で定義したデプロイマニフェストを取得して該当モジュール群をデバイス上に展開し、各モジュールの稼働状況をIoT Hubへ報告する。つまり「IoT Edgeランタイム」ときたら、その通信・管理の相手は必ずIoT Hubになる。
  • Azure IoT Central：IoT Hub等を土台にした、フルマネージドのSaaS型IoTアプリケーションプラットフォーム。バックエンドを自前で作り込まずに、GUI中心でIoTソリューションを素早く構築・運用したい場合に選ぶ。
IoT Hub vs Event Hubs（似ているが別物）
IoT Hub＝デバイス単位のID管理・双方向通信（クラウド→デバイスの制御）が可能。IoTシナリオに特化
Event Hubs＝大量データの高速取り込み（一方向：デバイス/送信元→クラウドのみ）に特化。個々の送信元の認証・双方向コマンド送信の概念はない
⚠ 「デバイスへコマンドを送りたい／デバイスごとに状態を管理したい」→ Event HubsではなくIoT Hub一択（Event Hubsはクラウドからデバイスへの送信経路を持たない）。「オフラインでも現場でリアルタイムに判断・処理したい」→ IoT Edgeでモジュールをデバイス側にデプロイ。「大量デバイスを自動的にIoT Hubへ登録したい」→ DPS。
IoT/大量テレメトリのリアルタイム処理パイプラインをどう組み立てるか → Event Hubs（IoT Hub）→ Stream Analytics → Functions が典型構成 頻出！
3段構成それぞれの役割
①取り込み：Event Hubs（またはIoT Hub）が大量デバイス/送信元からのストリームを高スループットで受信・バッファリングする
②処理：Stream Analyticsが、SQL風クエリでウィンドウ集計（例：5分間の平均値）・異常検知・フィルタリングなどをリアルタイムに実行する
③後続アクション：Stream Analyticsの出力（Output）としてAzure Functionsを呼び出し、しきい値超過時のアラート送信・DB書き込み・他システム連携等のカスタムロジックを実行する
  • Stream Analyticsの出力（Output）はFunctionsだけでなく、Power BI（リアルタイムダッシュボード）／Blob Storage・ADLS（アーカイブ）／Cosmos DB・SQL DB（永続化）／Service Bus・Event Hubs（他システムへの連携）など複数を同時に指定できる。「集計結果を可視化しつつ、異常値だけFunctionsでアラート」のような並列出力構成も可能。
  • この3段構成は「取り込み（Event Hubs/IoT Hub）」「ストリーム処理（Stream Analytics）」「カスタムロジック（Functions）」という役割分担が明確な疎結合パイプラインであり、IoT以外の大量ログ/クリックストリーム分析にも同じ構成パターンが使われる。
⚠ 試験では「大量のセンサーデータをリアルタイムで取り込み、異常検知して即座に通知したい」のような設問で、この3段構成のどこか1段を埋めさせる（例：「②に該当するのは？」）出題パターンが多い。取り込み段でデバイス個別のID管理・双方向通信が必要ならIoT Hub、そうでなければEvent Hubsで十分。
サービス間の疎結合・イベント駆動アーキテクチャを実現したい → Azure Event Grid
  • パブリッシャー（Blob作成・リソース変更等）→ Event Grid → サブスクライバー（Function・Logic Apps・Webhook）。
  • プッシュ型（サブスクライバーにイベントを配信）。ポーリング不要。
  • カスタムトピックを作成して独自イベントも発行できる。イベントサブスクリプションでは「イベントタイプ」等の条件でフィルタし、宛先ごとに必要なイベントだけ絞り込める。
  • イベントスキーマは既定の Event Grid スキーマのほか、業界標準の CloudEvents v1.0 スキーマも選択可能（他クラウド・OSSとの相互運用性を重視する場合はCloudEvents）。
  • 配信不能のイベントは設定したリトライポリシー（最大配信試行回数・イベント有効期間）に従って再試行され、それでも失敗した場合はデッドレター機能で指定したStorageアカウントのコンテナーへ退避できる（要設定。既定では無効）。
Event Hubsで複数チーム・アプリが同じストリームを独立して読み取り、かつ生データを保存したい → コンシューマーグループ + Capture機能
  • コンシューマーグループ：同一Event Hub内のイベントストリームを、チームやアプリごとに独立したビュー（オフセット管理も分離）で読み取れる。
  • Capture機能：受信したイベントを自動的にBlob StorageまたはADLS Gen2にAvro形式で保存。追加コードなしで設定するだけでアーカイブ・後段のバッチ分析に使える。
  • ⚠ Basicティアの制約：Capture機能は利用不可・コンシューマーグループは1個のみ・保持期間は1日固定。複数チームでの独立読み取りやCaptureが要件ならStandard以上が必要。
関連するメッセージ群の順序保証や、処理に失敗したメッセージの隔離が必要 → Service Bus セッション + Dead-Letter Queue（DLQ）
  • セッション：同じセッションIDを持つメッセージ群をまとめてFIFOで処理し、順序を保証したい場合に使う。
  • DLQ：配信不能・期限切れ・処理失敗したメッセージを自動的に隔離し、メインキューの詰まりを防ぐ。
  • Premiumティア：専用リソースで高スループット・最大100MBの大きいメッセージに対応し、VNet統合・プライベートエンドポイントも利用できる。

Functions vs Logic Apps
Functions = コード（C#/Python/JS等）で記述。開発者向け
Logic Apps = GUIでワークフローを組み立て。300以上のコネクタ。ノーコード向け
Logic Appsにも2つのホスティングモデルがある。Consumption＝マルチテナント・従量課金・PaaSコネクタ中心。Standard＝単一テナント（Workflow Standardプラン、App Service上で稼働）でVNet統合や安定した処理能力が必要な場合に選ぶ。

複雑なロジックをコードで表現したい（ループ・条件分岐が複雑） → Durable Functions
ノーコードで300以上のコネクタを使いGUIで組み立てたい → Logic Apps（Consumption）
ノーコードだがVNet統合・単一テナントの安定性能が必要 → Logic Apps（Standard）

複数の処理を並列実行して結果を集約したい／外部からの承認・イベントを待って処理を再開したい → Durable Functions のオーケストレーションパターン 頻出！
  • 関数チェーン（Function Chaining）：複数の関数を順番に呼び出し、前段の出力を次段の入力として渡す最も基本的なパターン（例：注文受付→在庫確認→決済→通知）。
  • ファンアウト/ファンイン：複数の処理を並列に実行し、すべて完了したら結果を集約する（例：多数ファイルを並列処理→まとめて集計）。
  • 外部イベント待機（人による承認など）：注文承認のように人の操作やコールバックが完了するまでオーケストレーションを一時停止しておき、外部からの通知を受けて処理を再開できる。タイムアウトも設定可能。
  • モニターパターン：一定間隔でポーリングしながら状態の変化を待つ処理を実装できる。
  • アグリゲーター（Durable Entities）：外部からのイベントを時間経過とともに集約・状態管理する、アドレス可能な小さな状態機械（エンティティ）。IoTデバイスのカウンタ集計など、状態を持つミニサービスとして扱える。
  • オーケストレーションの状態はランタイムが自動的に永続化するため、途中で失敗しても再実行に強い。
⚠ 複雑な多段階ワークフローをコードで表現したい場合はDurable Functions。GUIでの可視化やノーコード連携（多数の既製コネクタ）が主目的ならLogic Appsを検討する。

  • 機能フラグ：コード変更・再デプロイなしに機能のON/OFFを切り替えられる。カナリアリリースや段階的ロールアウトなどのリリース制御に使う。
  • アクセスには Microsoft Entra ID のマネージドIDを使い、接続文字列をコードや設定に埋め込まずに認証できる。

マイクロサービス・コンテナ
コンテナイメージのビルド・格納・自動更新をマネージドに行いたい → Azure Container Registry（ACR）＋ ACR Tasks 頻出！
  • Azure Container Registry（ACR）：Dockerコンテナイメージ・Helmチャート等を格納するプライベートなマネージドレジストリ。AKS/Container Apps/App Serviceなど各種コンピューティングサービスから直接イメージをpullできる。
  • ACR Tasks：ACR上でコンテナイメージのビルド・プッシュ・テストをクラウド側で自動実行する機能群。ローカルにDockerデーモンを用意しなくてもdocker build相当の処理をAzure側で実行できる（Quick Task）。
ACR Tasksの3つの自動トリガー
ベースイメージ更新トリガー
きっかけ：参照しているベースイメージ（OSパッチ等）が更新された時
用途：依存する全イメージを自動的に再ビルドし、パッチ適用漏れを防ぐ
ソースコードコミットトリガー
きっかけ：GitHub/Azure Reposへのコミット
用途：アプリコードの変更を検知して自動的にイメージを再ビルド
スケジュールトリガー
きっかけ：cron形式で指定した時刻
用途：定期的な再ビルド・メンテナンスタスクの実行
⚠ 「Docker Hub等のベースイメージが更新されたら、それに依存するカスタムイメージを自動的に再ビルドしたい」→ ACR Tasksのベースイメージ更新トリガーが正解（Azure DevOpsパイプラインを都度手動トリガーする必要がない）。複数ステップ（ビルド→テスト→プッシュ）を1つのワークフローにまとめたい場合はYAMLで定義するマルチステップタスクを使う。

マイクロサービス間の連携スタイルを設計したい → コレオグラフィ（Choreography） / オーケストレーション（Orchestration）
Choreography vs Orchestration
コレオグラフィ = 各サービスがイベントを発行/購読し、中央制御なしに自律的に連携（例：Event Grid/Event Hubs経由）。疎結合だが全体フローは追いにくい
オーケストレーション = 中央のコントローラー（Logic Apps・Durable Functions等）が各サービスの呼び出し順序を管理。フローの可視性は高いが中央への依存度が上がる
レガシー・外部システムのデータモデルを新システムに汚染させたくない → アンチコラプション レイヤー（ACL）パターン
  • 新旧（または自システムと外部システム）の間に変換層を置き、レガシー側のデータモデル/インターフェースを新システム用のモデルに変換してから受け渡す。
  • Strangler Figパターンで段階的移行する際、新旧システムが共存する期間の整合性を保つためによく併用される。
リアルタイム通信・非同期パターン
サーバーからクライアントへリアルタイムにデータをプッシュしたい（チャット・通知・ライブダッシュボード等） → Azure SignalR Service
  • WebSocket等を用いた双方向リアルタイム通信をマネージドで提供。大量の同時接続の管理をアプリ本体から切り離せる。
  • サービスモードはDefault（ハブサーバーあり。通常のASP.NET Core SignalR等の常時接続構成）／Serverless（Functions等と連携し、ハブサーバー不要）／Classic（旧アプリとの互換用レガシーモードで新規・既存とも非推奨）の3種類。ハブサーバーを持つ通常の常時接続構成はDefaultモードを選ぶ。
  • 大量の同時接続でも、App Service/Functions側のリソース負荷を増やさずにスケールできる。
時間のかかる処理をAPI経由で開始し、完了をクライアントに確認させたい → 非同期リクエスト・リプライ パターン
  • クライアントの初回リクエストに対し、即座に HTTP 202 Accepted と状態確認用URL（Locationヘッダー等）を返す。
  • クライアントはそのURLを定期的にポーリングし、処理完了後に結果を取得する。
  • Durable Functionsは、このHTTPスターター＋状態照会エンドポイントによる非同期パターンを組み込みでサポートする。
アーキテクチャパターン
大量の同時リクエストでもスケールするWebアプリを設計したい → ステートレス設計 + 水平スケール + 多層キャッシュ 頻出！
  • セッション状態をRedisに外部化（ステートレス化）→ App Serviceのインスタンスを自由にスケール。
  • 読み取り負荷 → Cache-Aside パターン（キャッシュになければDBから取得してキャッシュに書く）。
キャッシュ層の選択（多層キャッシュ）
グローバルなエッジでの静的/準静的コンテンツキャッシュ → Front Door エッジキャッシュ
API層でバックエンド応答をゲートウェイ側にキャッシュ → APIM 応答キャッシュ（cache-lookup/cache-store）
アプリ/DB層のCache-Asideやセッション外部化 → Azure Cache for Redis
単一インスタンス内だけで完結する超低遅延キャッシュ → プロセス内（インメモリ）キャッシュ
⚠ Redisのティア差：Basic/Standard＝開発・小規模向け（Standardはレプリカで可用性）。Premium＝永続化（RDB/AOF）・クラスタリング・VNet統合・受動的geo-replicationに対応。Enterprise/Enterprise Flash＝Redis Enterprise基盤で、RediSearch等のモジュールやアクティブ地理レプリケーション（マルチライト）に対応する上位SKU。
時間帯で決まった負荷とスパイクの両方に対応するオートスケールを設計したい → スケジュールルール + メトリックルールの組み合わせ
  • App Serviceのオートスケール設定では、スケジュールプロファイル（曜日・時間帯ごとの最小/最大/既定インスタンス数）とCPU使用率等のメトリックベースのスケールルールを同一プロファイル内で組み合わせられる。
  • 例：平日9-18時のプロファイルで最小5台を保証しつつCPU80%超で追加スケールアウト。夜間・休日は別プロファイルで最小1台に縮小してコスト削減。
  • Container AppsではKEDAスケーラーでキュー長等のカスタムメトリックに基づきスケールし、最小レプリカ数を0にすることでアイドル時のコストをゼロにできる（イベント駆動のバッチ/非同期ワーカー向け）。
レガシーモノリスをクラウドネイティブに段階的移行したい → Strangler Fig パターン
  • 既存システムを残しながら、機能を少しずつマイクロサービスに切り出す。
  • Azure API ManagementやAzure Front Doorをファサードとして置き、背後のルーティングを切り替えながら移行。
