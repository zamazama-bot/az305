Azure ADの多要素認証を強制したい → Conditional Access（条件付きアクセス） 頻出！
  • 「誰が・どのアプリに・どの条件で」アクセスするかを制御するポリシーエンジン。
  • MFA要求・準拠デバイス要件・特定IPブロックなどを組み合わせられる。
  • 条件：ユーザー/グループ・クラウドアプリ・名前付きの場所（Named Location）・デバイスプラットフォーム・クライアントアプリ（レガシー認証の一括ブロックを含む）。
  • 制御：ブロック、MFA要求、準拠デバイス要求、利用規約（Terms of Use）への同意、セッション制御（サインイン頻度短縮・永続ブラウザーセッション無効化）。
  • Azure AD Premium P1 以上が必要。
⚠ セキュリティデフォルト（無料）と混同しない。カスタムポリシーが必要なら必ずConditional Access。
サインイン時の異常や漏えい資格情報を検知して自動対応したい → Identity Protection（サインインリスク・ユーザーリスクポリシー） 頻出！
  • Microsoft Entra ID P2が必要。Conditional Access内のリスク条件として構成する。
  • サインインリスク：その場のサインイン試行の異常度（不審な場所・匿名IP等）を評価 → ブロックまたはMFA要求。
  • ユーザーリスク：アカウント自体の漏えい可能性（漏えい資格情報の一致等）を評価 → 「高」リスク時にパスワード変更を必須にする。
その場限りの怪しいサインインを止めたい → サインインリスクポリシー
アカウント自体が漏えいしている疑い → ユーザーリスクポリシー（パスワード変更必須）
⚠ サービスアカウント等は除外設定し、リスク検出結果はLog Analytics/Sentinelへ転送して監視するのが定石。
特に重要な操作にフィッシング耐性のある強い認証を要求したい → Conditional Access の認証強度（Authentication Strength）
  • 組み込みの強度：MFA／パスワードレスMFA／フィッシング耐性MFA（FIDO2セキュリティキー、証明書ベース認証、Windows Hello for Business）。
  • 単に「MFAを要求」するより、許容する認証方法の組み合わせを細かく指定できる。
アプリがAzureリソースにアクセスする（パスワード不要） → マネージドID（Managed Identity） 頻出！
  • システム割り当て：リソースに1対1で紐付く。リソース削除で自動削除。
  • ユーザー割り当て：複数リソースで共有可能。ライフサイクルを独立管理。
  • 同じ権限を多数のリソースに与えるだけなら、ユーザー割り当てMIを1つ作成して使い回すのが最も効率的。環境（dev/test/prod）ごとに分離したい場合はテンプレートで環境別に事前作成し、リソースIDを参照する。
アプリのキー/パスワード管理が不要になる → Key Vaultとセットで語られることが多い。
GitHub Actions / AKS等、Azure外のワークロードからシークレットなしでAzureにアクセスさせたい → ワークロードIDフェデレーション（Workload Identity Federation） 頻出！
  • アプリ登録（またはユーザー割り当てMI）にフェデレーション資格情報を構成し、外部IdPが発行するOIDCトークンを信頼する。
  • シークレット・証明書の管理が不要。GitHub Actions、他クラウドのワークロード、AKSのサービスアカウントなどが対象。
  • AKSでは「Microsoft Entraワークロード ID」を有効にし、Kubernetesサービスアカウントとフェデレーション資格情報を構成する。
最小権限でAzureリソースへのアクセスを管理したい → Azure RBAC（ロールベースアクセス制御） 頻出！
  • スコープ：管理グループ ＞ サブスクリプション ＞ リソースグループ ＞ リソース
  • Owner / Contributor / Reader が代表的な組み込みロール。
  • カスタムロールも作成可能（JSON定義）。Actions（管理操作）とDataActions（データ操作。例：BLOBの読み取り）を区別し、特定操作だけ除外したいときはNotActions/NotDataActionsを使う。
  • 継承は上位スコープ→下位スコープの一方向のみ。下位で付与したロールが上位に影響することはない。
RBAC vs Azure AD ロール
RBAC = Azureリソース（VM・ストレージ等）への権限管理
Azure AD ロール = Azure AD自体（ユーザー・グループ管理等）への権限管理
⚠ BLOBデータの読み取り等の「データプレーン操作」は、Reader/Contributorのような管理プレーンロールでは許可されない。Storage Blob Data ReaderのようなDataActionsを含むロールが必要。
外部ユーザー（取引先など）にAzure ADのアプリへアクセスさせたい → Azure AD B2B
  • 招待されたゲストユーザーが自社のAzure ADテナントにアクセス。
  • B2C（一般消費者向けID管理）と混同しない。
B2B vs B2C
B2B = 企業間コラボ（パートナー、取引先）
B2C = エンドユーザー向けアプリのID管理（Googleログイン等のソーシャルID連携）
旧Azure AD B2C → 現Microsoft Entra External ID。消費者向けアプリでセルフサービスのサインアップ/サインインを実装する場合に使用。
社外パートナーや監査法人に、期限付き・承認制でアプリ/グループへのアクセスを付与したい → 資格管理（Entitlement Management）のアクセスパッケージ 頻出！
  • アプリ・グループ・SharePointサイト等をまとめた「アクセスパッケージ」を作成し、承認フロー・有効期限・定期アクセスレビューを設定できる。
  • 接続済み組織（Connected Organization）を登録すると、Entra ID未導入の外部組織のユーザーもリクエスト対象にできる。
  • B2Bゲスト招待を都度手動で行うより、大規模・自動化されたガバナンスに向く。
Microsoft Entra ID P2が必要。
オンプレミスADのIDをEntra IDと同期したい → Microsoft Entra Connect Sync／Cloud Sync
  • パスワードハッシュ同期（PHS）：最もシンプル。シームレスSSOと組み合わせるとオンプレ資格情報でSSOできる。
  • パススルー認証（PTA）：オンプレ側エージェントでパスワードを検証。ハッシュはクラウドに送らない。
  • フェデレーション（AD FS等）：既存の外部IdPをそのまま使いたい場合。
  • Cloud Sync：軽量プロビジョニングエージェント。買収などで互いに信頼関係のない複数のオンプレADフォレストを1つのテナントに同期する場合に有利。
ユーザー自身にパスワードをリセットさせ、オンプレADにも反映したい → SSPR（セルフサービスパスワードリセット）＋ パスワード書き戻し
  • SSPRはP1以上で有効化（一部機能はFreeでも可）。ハイブリッド環境ではEntra Connectでパスワードライトバックを有効にしてオンプレADにも反映させる。
ガバナンス
全サブスクリプションに一律ルールを強制したい（例：特定リージョンのみ許可） → Azure Policy 頻出！
  • 準拠していないリソースを検出・拒否・自動修復できる。
  • 管理グループに割り当てて組織全体に適用するのが典型パターン。
  • イニシアチブ（Initiative）＝複数ポリシーをまとめたセット。
  • 親スコープのポリシーから特定サブスクリプション/リソースだけ除外したい → ポリシー例外（Exemption）を使う（ポリシー自体を作り直す必要はない）。
  • 一時的にポリシーの拒否評価を止めたい → 割り当ての強制モード（Enforcement mode）をDoNotEnforceにする（コンプライアンス評価・ログは継続するが拒否は行わない）。
Azure Policy の効果（Effect）比較
Deny
動作作成/更新を拒否
Append
動作作成時にフィールド追加
Modify
動作既存リソースも更新可
Audit
動作非準拠を記録のみ
AuditIfNotExists
動作関連リソース欠如を監査
DeployIfNotExists
動作欠如していれば自動デプロイ
⚠ Append/Modifyは「作成をブロックせず値を強制」、DeployIfNotExists/AuditIfNotExistsは「関連リソース（診断設定等）の有無」をチェックする点で対象が異なる。DeployIfNotExistsの実行にはマネージドIDが必要。RBACと混同注意：RBACは「誰が何をできるか」、Policyは「何を作れるか」のルール。
複数サブスクリプションを階層管理したい → 管理グループ（Management Groups） 頻出！
  • 最大6階層（ルート管理グループ含む）。
  • Azure Policy・RBAC を管理グループに割り当てると配下のサブスクリプションに継承される。
  • 大企業の組織構造（部門別サブスク）をそのまま反映できる。
  • Landing Zone設計の定石：ルート直下の中間管理グループ（プラットフォーム/ランディングゾーン等）に共通イニシアチブを1回割り当て、配下の環境別管理グループやサンドボックスにはポリシー例外で個別調整する。
リソースの誤削除・誤変更を防ぎたい → リソースロック（Resource Locks）
  • CanNotDelete：削除不可・変更は可。
  • ReadOnly：削除・変更ともに不可（= 読み取り専用）。
  • 所有者でもロック解除しなければ削除できない。
コストタグ付け・リソースのグループ化・テンプレートデプロイを一括管理したい → Azure Blueprints / Landing Zone
  • Blueprints = Policy・RBAC・ARMテンプレートを1パッケージにして繰り返しデプロイ。
  • Landing Zone = 大規模組織向けの推奨アーキテクチャパターン（CAF準拠）。
⚠ Blueprintsは非推奨方向。新規案件ではテンプレート仕様（Template Specs）＋デプロイスタック（Deployment Stacks）の組み合わせが推奨される。
テンプレートでデプロイした一式のリソースを、誰であっても削除・変更できないよう一括ロックしたい → デプロイスタック（Deployment Stacks）＋ denySettings
  • 複数リソースをまとめて1つの「スタック」として管理し、denySettingsで削除・変更操作をスタック単位で拒否できる。
  • 個々のリソースに1つずつロックを設定する手間を省ける。ARM/Bicepデプロイと統合されている。
コスト・マルチテナント管理
コストが予算を超えそうなときに複数段階で通知したい → Cost Management の予算（Budget）＋ アクショングループ
  • 予算に複数のしきい値（例：50%/80%/100%）を設定し、超過時にメール通知やアクショングループ（Webhook/Functions等）を呼び出せる。
リソースのタグは変更せず、コストレポート上だけ親スコープのタグを継承させたい → Cost Management の「タグ継承（Tag Inheritance）」
  • サブスクリプション/管理グループのタグをコストデータに仮想的に適用する機能。実リソースのタグ自体は書き換えない。
安定稼働するVM/DB等のコストを長期契約で削減したい → Azure予約（Reservations）
  • 1年/3年の予約でオンデマンド比最大約70%割引。スコープを「共有」にすると組織内の複数サブスクリプションで消費可能。
  • インスタンスサイズの柔軟性が有効なVMシリーズなら、同一シリーズ内でサイズを変更しても割引が引き継がれる。
⚠ Savings Plan（使用量ベースのコミット割引）と混同しない：予約は特定リソースタイプ・数量に対する割引、Savings Planはコミット金額に対する柔軟な割引。
MSP/パートナーとして複数の顧客テナントのリソースを自社から一元管理したい → Azure Lighthouse
  • 顧客テナントのサブスクリプション/リソースグループへのアクセスを自社（管理側）テナントに委任し、テナントを跨いでまとめて運用・監視できる。
  • 顧客側はRBACロールの委任を許可するだけでよく、自社ユーザーを顧客テナントに個別作成する必要がない。
監視・セキュリティ
全リソースのログ・メトリクスを一元監視したい → Azure Monitor 頻出！
  • メトリクス（数値）＋ログ（Log Analytics）の両方を扱う統合監視サービス。
  • アラート → アクショングループ（メール/SMS/Webhook/Function/Automationランブック呼び出しなど）で自動対応。
  • データ収集ルール（DCR）＋Azure Monitorエージェント（AMA）：1台のエージェントに複数のDCRを関連付けられ、収集対象・頻度をDCR単位で一元管理できる。
  • メトリクスアラートは動的しきい値（Dynamic Thresholds）で過去の傾向から自動学習させられる。
  • アラート処理ルール（Alert Processing Rules）：メンテナンス期間中など特定条件下の通知だけを抑制できる（アラート自体の発報は止めない）。
  • Application Insights はアプリ専用の監視機能で、Monitorの一部。分散トレース＋アプリケーションマップでマイクロサービス間の依存関係・遅延を可視化。
診断設定（Diagnostic Settings）のログ・メトリクス送信先を使い分けたい → Log Analytics／ストレージアカウント／Event Hub（1つの診断設定で複数同時指定可） 頻出！
クエリ分析・アラート・Sentinel連携 → Log Analyticsワークスペース
低コストな長期保管・監査証跡 → ストレージアカウント（不変ストレージで改ざん防止も可）
外部SIEM連携・リアルタイムストリーミング → Event Hub
1つの診断設定内で3つの送信先を同時に有効化できる（例：短期分析はLog Analytics、長期アーカイブは不変ストレージ、外部SIEM連携はEvent Hub）。
Log Analyticsワークスペースを1つに集約すべきか、分割すべきか迷う → 要件（データ主権・アクセス分離・コスト）に応じて集約/分散を選ぶ
  • 集約（1ワークスペース）：横断クエリが容易で管理もシンプル。リージョンを跨ぐデータ転送コストやデータ主権要件に注意。
  • リージョン別に分散：各リージョンにワークスペースを作り、クロスワークスペースクエリ（union等）で横断分析する。データ主権・レイテンシ要件がある大規模組織向け。
  • テーブルレベルAzure RBAC：ワークスペース全体ではなく特定テーブルだけ読み取りを許可したい場合、テーブルごとにRBACロールを割り当て、アクセス制御モードも適切なモードへ変更する。
  • 保持設計：対話型（Interactive）保持は必要最小限にとどめ、それ以降は長期保持（アーカイブ）へ切り替えてコスト削減。アーカイブ済みデータは検索ジョブ（Search Job）や復元（Restore）で必要時のみ参照する。
Azureリソースの設定ミス・セキュリティリスクを継続的に評価したい → Microsoft Defender for Cloud（旧 Security Center） 頻出！
  • 無料の基盤機能（CSPM）：セキュアスコアの算出・推奨事項の提示のみ。脅威検出にはリソース種別ごとのDefenderプラン（Servers/SQL/Storage/Containers/Key Vault等）を個別に有効化する必要がある（有料）。
  • Just-In-Time（JIT）VMアクセス：Defender for Servers Plan 2の機能。通常はNSGでポートを閉じ、必要時のみ特定IPからの一時的な接続を許可する。
  • マルチクラウド（AWS・GCP）のリソースも監視対象にできる。
  • 規制コンプライアンスダッシュボードには、独自の統制項目をカスタムイニシアチブとして作成し「カスタム標準」として追加できる。
Azure全体のセキュリティインシデントをSIEMで管理したい → Microsoft Sentinel
  • クラウドネイティブSIEM/SOAR。Log Analyticsワークスペース上に構築。
  • データコネクタでログソース（Entra ID、Defender for Cloud等）を取り込み、分析ルール（Analytics Rules）が検知条件に一致するとインシデントを自動生成。
  • 近似リアルタイム（NRT）分析ルール：数分以内の低遅延検知が必要な限定シナリオ向け。通常の分析ルールよりスケジュール頻度が高い。
  • 自動化ルール（Automation Rules）からプレイブック（Logic Apps）を呼び出してインシデント対応を自動化。
シークレット・証明書・暗号化キーを安全に管理したい → Azure Key Vault 頻出！
  • Secrets（接続文字列等）・Keys（暗号化キー）・Certificates を一元管理。
  • ネットワーク制限：パブリックアクセスを無効化し「選択したネットワークのみ許可」＋信頼済みMicrosoftサービスのバイパスを有効化、または完全に閉じたい場合はPrivate Endpointを使用。
  • 論理的な削除（Soft Delete）は既定で有効。CMK（カスタマーマネージドキー）用途では、誤って完全削除されないようパージ保護（Purge Protection）も併せて有効化する。
  • アクセスモデル：アクセスポリシー（Vault単位の粗い制御）よりAzure RBAC（シークレット/キー単位の細かいスコープで組み込みロールを割り当て可能）が推奨。
  • マネージドIDと組み合わせてコードにシークレットを書かないのが正解パターン。

SQL Managed Instance で TDE＋カスタマーマネージドキー、暗号化強度を最大化したい → RSA 3072 頻出！
  • TDE（透過的データ暗号化）のカスタマーマネージドキーは Key Vault に置く RSA キー（非対称鍵）のみ。
  • サポートされるキー長は RSA 2048 と RSA 3072 のみ（RSA 4096 は対象外）。
  • 強度最大化 → RSA 3072（鍵長が長いほど強度が高い）。
⚠ AES-256 はデータ本体の暗号化（DEK）に使われる対称鍵でAzureが自動適用するもの。カスタマーが Key Vault で指定するのは RSA キー。混同しないこと。
特権アカウント（全体管理者等）へのアクセスをジャストインタイムで制御したい → Azure AD PIM（Privileged Identity Management） 頻出！
  • 通常は権限なし → 必要なときだけ一時的に昇格（承認フロー付き）。
  • 割り当て種別：適格（Eligible＝申請すれば有効化できる）とアクティブ（Active＝常時有効）を区別する。特権ロールは基本Eligibleにする。
  • ロール設定で、承認者による承認・MFA必須・理由/チケット番号の入力・最大アクティブ化期間（例：4時間）などを個別に構成できる。
  • PIM for Groups：ロールだけでなくグループのメンバーシップ/所有権自体もJIT化できる。グループに紐づく複数リソースへの権限をまとめてJIT管理したい場合に効率的。
  • 利用にはAzure AD Premium P2が必要。
  • アクセスレビューで定期的に権限の棚卸しも可能。

③ 事業継続性（DR・バックアップ・HA）
重要指標（必ず暗記）
RTO / RPO の定義 → RTO = 復旧時間目標　／　RPO = 復旧時点目標 頻出！
  • RTO（Recovery Time Objective）：障害発生からサービス復旧までの最大許容時間。
  • RPO（Recovery Point Objective）：障害発生時に許容できる最大データ損失時間。
判断の基準
RTO短い = サービス止められない → 自動フェールオーバー必須
RPO短い = データ損失NG → 同期レプリケーション or 高頻度バックアップ
「RTO=0, RPO=0」の要件 → Active-Active 構成（Azure Traffic Manager + 複数リージョン）。
RPO計算の具体例（最後の成功バックアップ〜障害発生までの実測）
前日 22:00 → 最後に成功したバックアップ
当日 14:00 → 障害発生（データ消失）
RPO = 14:00 − 前日22:00 = 約16時間（データ損失）
⚠ RPOは「バックアップの実行間隔（例: 1日1回）」そのものではない。実際のRPOは障害発生タイミング次第で0時間〜ほぼ間隔と同じ時間の範囲で変動する、実測ベースの値。ASRのような継続的レプリケーションはRPOを数分〜数十分まで短縮できる。

Recovery Services コンテナー vs Backup コンテナー（Backup vault）
Recovery Services コンテナー = VM／Azure Files（スナップショット）／SQL Server on Azure VM／SAP HANA on Azure VM

⚠ 3種類混在（VM・SQL・Blob）の要件では「VM・SQLはRecovery Servicesコンテナー、BlobはBackupコンテナー」の組み合わせが必須。1つのコンテナー種別にまとめることはできない。

  • Backup vaultの冗長性を地理冗長（GRS等）にすればリージョン障害にも対応。
⚠ 混同注意：Blobの「バージョニング＋ポイントインタイムリストア（運用バックアップ）」は同一アカウント内保持のため、アカウント削除・侵害には無力。「オブジェクトレプリケーション」はバックアップではなくレプリケーション（ソースでの削除・暗号化がターゲットに伝播しうる）。真のランサムウェア対策には vaulted バックアップが必要。

  • 1つの日次スケジュールから週次・月次・年次の復元ポイントを選び、それぞれ独立した保持期間を設定できる（標準・拡張ポリシーとも対応）。

ディザスタリカバリ（DR）
VMやオンプレサーバーのDRを自動化したい → Azure Site Recovery（ASR） 頻出！
  • Azure → Azure / オンプレ → Azure / Azure → オンプレ のレプリケーションが可能。
  • フェールオーバーテストを本番に影響なく実施できる（本番・オンプレと接続しない分離テスト用VNetを指定）。
  • RPO は数秒〜数分、RTOは数分〜数時間（ポリシー次第）。
  • リカバリプラン：複数VMをグループ化し、グループ単位で起動順序（ブートオーダー）を定義。Automationランブックのステップを前後に挿入して、DNS更新等も自動化できる。
  • Hyper-Vからのレプリケーションは System Center VMM 経由に加え、VMMなしでHyper-Vホストに直接Providerを登録する構成にも対応（小規模拠点向け）。
⚠ 「DB起動後にアプリ→Webの順で立ち上げたい」等の多層システムの起動順序制御 → リカバリプランが正解（レプリケーションポリシーの保持期間設定ではない）。
⚠ Azure Backup の geo リストアは別リージョンへの新規作成による復元のため数時間規模かかる。「RTO数十分以内」等の短いRTO要件には使えない → ASR かフェールオーバーグループ等の常時レプリケーション型を使う。
Azureのリージョンペアが自動的にやってくれること／やってくれないこと → ペアは"土台"にすぎない。DRは別途構成が必要
  • 自動で得られるのは「広域障害時にペアの一方が優先的に復旧される」「計画的なプラットフォームメンテナンスがペア間で時間差をつけて順番に展開される」の2点のみ。
  • VMの自動レプリケーション・自動フェールオーバーはされない（ASR等を別途構成）。
  • ストレージの冗長性（LRS→GRS等）も自動では切り替わらない（作成時・変更時に明示的な選択が必要）。
  • DNSの自動相互フェールオーバーも行われない（Traffic Manager / Front Door 等を別途構成）。
⚠「リージョンペア＝DR」ではない。ペアはMicrosoft運用上の性質にすぎず、実際のDRはSite Recovery・SQLフェールオーバーグループ・Traffic Manager/Front Doorなど具体的なサービスの組み合わせで実現する。
本番環境への影響を抑えつつ耐障害性を継続的に検証したい → Azure Chaos Studio
  • 可用性ゾーン停止・VMのCPU/メモリストレス・ネットワーク遅延やパケットロス注入などの障害を、制御された実験としてスコープ・時間・安全対策（緊急停止条件）を定義して注入。
  • リージョン全体の切り替えを伴わない、粒度の細かいレジリエンス検証に向く。
⚠ ASRのテストフェールオーバーはリージョン単位の大掛かりなDR検証、Chaos Studioはゾーン障害・レイテンシ等の粒度の細かい障害注入検証、と使い分ける。負荷試験（Azure Load Testing）やアラート閾値の一時変更は障害注入の代替にはならない。

  • Firewall Policy：親（ベース）ポリシーに全社共通ルールを定義し、子ポリシーに継承させて事業部門ごとにルールを委任・追加できる。

サブネット内のVM群を役割ごとにグルーピングしてNSGルールを簡潔にしたい → アプリケーションセキュリティグループ（ASG）
NSG vs ASG
NSG（ネットワークセキュリティグループ）= サブネット/NICに適用するL3-L4のアクセス制御リスト本体
ASG（アプリケーションセキュリティグループ）= VMを役割（Web/DB等）でグループ化するラベル。NSGルールの送信元/宛先にASGを指定することでIPアドレスを意識せずルールを記述できる
ASG単体では通信を制御できない。必ずNSGルールの中で「送信元/宛先」として参照する形で使う。
AzureサービスへのアクセスをVNet内に閉じたい（パブリックIP不要） → プライベートエンドポイント（Private Endpoint） 頻出！
  • Blob・SQL・Key Vaultなどに対してVNet内のプライベートIPアドレスを割り当てる。
  • インターネットを経由せずにAzureサービスへアクセス可能。
  • プライベートエンドポイントを使う場合、対応する privatelink.*.core.windows.net 等のプライベートDNSゾーンを作成しVNetにリンクしないと名前解決がパブリックIPのままになる（例：Blobならprivatelink.blob.core.windows.net）。
Private Endpoint vs Service Endpoint
Private Endpoint = VNet内にプライベートIPを作成。より強固な分離。他社（別テナント）へも自サービスを公開できる
Service Endpoint = VNetからAzureサービスへの経路最適化。パブリックIPは残る
⚠ 自分が構築したPaaSライクなサービス（例：内部Load Balancer配下のサービス）を他のVNet/他テナントの顧客に安全に公開したい場合はPrivate Linkサービスを内部LB上に作成する。顧客側は自分のVNetにプライベートエンドポイントを作成して接続する（提供側＝Private Linkサービス／利用側＝プライベートエンドポイント、の対応関係を混同しない）。
Azure DNSの機能を使い分けたい（パブリック/プライベートゾーン） → 用途別にゾーン種別・機能を選択
  • パブリックDNSゾーン：インターネット向けの権威DNS。レジストラー側のNSレコードをAzure DNSの名前サーバーに向けて委任する。
  • プライベートDNSゾーン：VNet内限定の名前解決。自動登録（Auto registration）を有効にすると、リンクしたVNet内のVMのDNSレコードが自動作成・更新される。
  • プライベートDNSゾーン（privatelink）：プライベートエンドポイントの名前解決に使用。
  • エイリアスレコード：Azure リソース（Traffic Manager・Public IP・Front Doorなど）を直接参照するDNSレコード。ゾーンのapex（ルートドメイン）でもCNAME相当の動きを実現できる（例：apexをTraffic Managerプロファイルに向ける）。
  • Azure DNS Private Resolver：オンプレとAzure間でDNSクエリを相互転送するマネージドサービス。VNet内にリゾルバーを置きハイブリッドDNS解決を実現。
「ゾーンのapexドメインをAzureリソースに向けたい（CNAMEはapexに使えない）」→ エイリアスレコード。「オンプレとAzureのDNSを相互に名前解決したい」→ Azure DNS Private Resolver。
大量の送信接続でSNATポートが枯渇しエラーが発生する → NAT Gateway を配置する 頻出！
  • Standard Load Balancerの既定のアウトバウンドSNATはポート数が限られ、大量の同時アウトバウンド接続（特に同一宛先への多数接続）でポート枯渇が起こりやすい。
  • NAT Gatewayをサブネットに関連付けると、静的なパブリックIP（またはIPプレフィックス）で送信元を固定しつつ、SNATポートを効率的かつ大量に割り当てられる。
  • VMSS/AKS等、多数のインスタンスが外部へ大量の接続を張るワークロードで定番の対処。
⚠ 「間欠的に接続エラーが起きる」「同一宛先への大量アウトバウンド接続」というキーワードが出たらSNATポート枯渇を疑い、NAT Gatewayまたは明示的なアウトバウンドルールでのポート割り当て増加を検討する。
DDoS攻撃からパブリックIPを保護したい → DDoS Protection（IP Protection / Network Protection）
  • Basic：すべてのAzureパブリックIPに既定で無料・自動適用。追加設定不要だが検知・通知等の高度な機能はなし。

Webアプリを外部アクセスなしにVNet内から安全に公開したい → App Service + VNet統合 / App Service Environment（ASE）
  • VNet統合：App ServiceからVNet内のリソースへのアウトバウンド接続を有効化。
  • Private Endpoint for App Service：App ServiceへのインバウンドをVNet内に限定。
  • ASE（App Service Environment）：完全にVNet内に配置する専用環境（高コスト・高セキュリティ）。

サービス間の疎結合・イベント駆動アーキテクチャを実現したい → Azure Event Grid
  • パブリッシャー（Blob作成・リソース変更等）→ Event Grid → サブスクライバー（Function・Logic Apps・Webhook）。
  • プッシュ型（サブスクライバーにイベントを配信）。ポーリング不要。
  • カスタムトピックを作成して独自イベントも発行できる。イベントサブスクリプションでは「イベントタイプ」等の条件でフィルタし、宛先ごとに必要なイベントだけ絞り込める。
  • イベントスキーマは既定の Event Grid スキーマのほか、業界標準の CloudEvents v1.0 スキーマも選択可能（他クラウド・OSSとの相互運用性を重視する場合はCloudEvents）。
Event Hubsで複数チーム・アプリが同じストリームを独立して読み取り、かつ生データを保存したい → コンシューマーグループ + Capture機能
  • コンシューマーグループ：同一Event Hub内のイベントストリームを、チームやアプリごとに独立したビュー（オフセット管理も分離）で読み取れる。
  • Capture機能：受信したイベントを自動的にBlob StorageまたはADLS Gen2にAvro形式で保存。追加コードなしで設定するだけでアーカイブ・後段のバッチ分析に使える。
関連するメッセージ群の順序保証や、処理に失敗したメッセージの隔離が必要 → Service Bus セッション + Dead-Letter Queue（DLQ）
  • セッション：同じセッションIDを持つメッセージ群をまとめてFIFOで処理し、順序を保証したい場合に使う。
  • DLQ：配信不能・期限切れ・処理失敗したメッセージを自動的に隔離し、メインキューの詰まりを防ぐ。
  • Premiumティア：専用リソースで高スループット・最大100MBの大きいメッセージに対応し、VNet統合・プライベートエンドポイントも利用できる。
API管理・統合
複数のバックエンドAPIを一元管理・保護・監視したい → Azure API Management（APIM） 頻出！
  • APIゲートウェイ：レート制限・認証・キャッシュ・変換をポリシーで設定。
  • 開発者ポータルで APIドキュメント・テスト環境を自動公開。
  • バックエンドはAzure FunctionでもオンプレAPIでも可。
⚠ オンプレミスや他クラウドにあるバックエンドを公開したい場合は「セルフホステッドゲートウェイ」をコンテナとしてそちら側にデプロイしつつ、管理・ポリシー設定はAzure上のAPIMインスタンスから一元的に行える（ハイブリッド/マルチクラウド公開）。
APIの呼び出し回数を制限したり、リクエスト/レスポンスの形式を変換したい → API Management ポリシー 頻出！
  • rate-limit-by-key：サブスクリプションキーやIPアドレスなど任意のキー単位で呼び出し回数を制限。テナント（呼び出し元）ごとのスロットリングに使う。
  • xml-to-json / json-to-xml：レガシーなSOAP/XML APIをJSONとして公開するなど、バックエンドを変更せずに形式を変換できる。
  • cache-lookup / cache-store：バックエンドの応答をゲートウェイ側でキャッシュし、バックエンドへの負荷とレイテンシを削減。
  • ポリシーはXMLベースの設定で、inbound（受信時）/ backend（バックエンド呼び出し前後）/ outbound（応答時）/ on-error（エラー時）の各パイプライン段階に適用できる。

サーバーレス・自動化
イベントに応じて短時間のコードを実行したい（サーバーレス） → Azure Functions 頻出！
  • トリガー：HTTP / Timer / Blob / Queue / Event Hub / Service Bus / Event Grid など多数。
  • 消費プラン（サーバーレス）：実行回数・時間で課金。自動スケール。
  • Durable Functions：複数ステップのワークフローをオーケストレーション。
Functions vs Logic Apps
Functions = コード（C#/Python/JS等）で記述。開発者向け
Logic Apps = GUIでワークフローを組み立て。300以上のコネクタ。ノーコード向け
Logic Appsにも2つのホスティングモデルがある。Consumption＝マルチテナント・従量課金・PaaSコネクタ中心。Standard＝単一テナント（Workflow Standardプラン、App Service上で稼働）でVNet統合や安定した処理能力が必要な場合に選ぶ。
複数の処理を並列実行して結果を集約したい／外部からの承認・イベントを待って処理を再開したい → Durable Functions のオーケストレーションパターン 頻出！
  • ファンアウト/ファンイン：複数の処理を並列に実行し、すべて完了したら結果を集約する（例：多数ファイルを並列処理→まとめて集計）。
  • 外部イベント待機（人による承認など）：注文承認のように人の操作やコールバックが完了するまでオーケストレーションを一時停止しておき、外部からの通知を受けて処理を再開できる。タイムアウトも設定可能。
  • モニターパターン：一定間隔でポーリングしながら状態の変化を待つ処理を実装できる。
  • オーケストレーションの状態はランタイムが自動的に永続化するため、途中で失敗しても再実行に強い。
⚠ 複雑な多段階ワークフローをコードで表現したい場合はDurable Functions。GUIでの可視化やノーコード連携（多数の既製コネクタ）が主目的ならLogic Appsを検討する。

Choreography vs Orchestration
コレオグラフィ = 各サービスがイベントを発行/購読し、中央制御なしに自律的に連携（例：Event Grid/Event Hubs経由）。疎結合だが全体フローは追いにくい
オーケストレーション = 中央のコントローラー（Logic Apps・Durable Functions等）が各サービスの呼び出し順序を管理。フローの可視性は高いが中央への依存度が上がる
レガシー・外部システムのデータモデルを新システムに汚染させたくない → アンチコラプション レイヤー（ACL）パターン
  • 新旧（または自システムと外部システム）の間に変換層を置き、レガシー側のデータモデル/インターフェースを新システム用のモデルに変換してから受け渡す。
  • Strangler Figパターンで段階的移行する際、新旧システムが共存する期間の整合性を保つためによく併用される。
リアルタイム通信・非同期パターン
サーバーからクライアントへリアルタイムにデータをプッシュしたい（チャット・通知・ライブダッシュボード等） → Azure SignalR Service
  • WebSocket等を用いた双方向リアルタイム通信をマネージドで提供。大量の同時接続の管理をアプリ本体から切り離せる。
  • サーバーレス（Functions等）と組み合わせる「サーバーレスモード」と、常時接続を扱う「クラシックモード」がある。
  • 大量の同時接続でも、App Service/Functions側のリソース負荷を増やさずにスケールできる。
時間のかかる処理をAPI経由で開始し、完了をクライアントに確認させたい → 非同期リクエスト・リプライ パターン
  • クライアントの初回リクエストに対し、即座に HTTP 202 Accepted と状態確認用URL（Locationヘッダー等）を返す。
  • クライアントはそのURLを定期的にポーリングし、処理完了後に結果を取得する。
  • Durable Functionsは、このHTTPスターター＋状態照会エンドポイントによる非同期パターンを組み込みでサポートする。
アーキテクチャパターン
大量の同時リクエストでもスケールするWebアプリを設計したい → ステートレス設計 + 水平スケール + キャッシュ
  • セッション状態をRedisに外部化（ステートレス化）→ App Serviceのインスタンスを自由にスケール。
  • CDN で静的コンテンツをキャッシュ → オリジンへの負荷軽減。
  • 読み取り負荷 → Cache-Aside パターン（キャッシュになければDBから取得してキャッシュに書く）。
時間帯で決まった負荷とスパイクの両方に対応するオートスケールを設計したい → スケジュールルール + メトリックルールの組み合わせ
  • App Serviceのオートスケール設定では、スケジュールプロファイル（曜日・時間帯ごとの最小/最大/既定インスタンス数）とCPU使用率等のメトリックベースのスケールルールを同一プロファイル内で組み合わせられる。
  • 例：平日9-18時のプロファイルで最小5台を保証しつつCPU80%超で追加スケールアウト。夜間・休日は別プロファイルで最小1台に縮小してコスト削減。
  • Container AppsではKEDAスケーラーでキュー長等のカスタムメトリックに基づきスケールし、最小レプリカ数を0にすることでアイドル時のコストをゼロにできる（イベント駆動のバッチ/非同期ワーカー向け）。
レガシーモノリスをクラウドネイティブに段階的移行したい → Strangler Fig パターン
  • 既存システムを残しながら、機能を少しずつマイクロサービスに切り出す。
  • Azure API ManagementやAzure Front Doorをファサードとして置き、背後のルーティングを切り替えながら移行。
