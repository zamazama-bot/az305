AZ-305 チートシート

Microsoft Azure Solutions Architect Expert ／ 公式スキルアウトライン準拠

① ID・ガバナンス・監視
認証・認可
Azure ADの多要素認証を強制したい → Conditional Access（条件付きアクセス） 頻出！
  • 「誰が・どのアプリに・どの条件で」アクセスするかを制御するポリシーエンジン。
  • MFA要求・準拠デバイス要件・特定IPブロックなどを組み合わせられる。
  • Azure AD Premium P1 以上が必要。
⚠ セキュリティデフォルト（無料）と混同しない。カスタムポリシーが必要なら必ずConditional Access。
アプリがAzureリソースにアクセスする（パスワード不要） → マネージドID（Managed Identity） 頻出！
  • システム割り当て：リソースに1対1で紐付く。リソース削除で自動削除。
  • ユーザー割り当て：複数リソースで共有可能。ライフサイクルを独立管理。
アプリのキー/パスワード管理が不要になる → Key Vaultとセットで語られることが多い。
最小権限でAzureリソースへのアクセスを管理したい → Azure RBAC（ロールベースアクセス制御） 頻出！
  • スコープ：管理グループ ＞ サブスクリプション ＞ リソースグループ ＞ リソース
  • Owner / Contributor / Reader が代表的な組み込みロール。
  • カスタムロールも作成可能（JSON定義）。
RBAC vs Azure AD ロール
RBAC = Azureリソース（VM・ストレージ等）への権限管理
Azure AD ロール = Azure AD自体（ユーザー・グループ管理等）への権限管理
外部ユーザー（取引先など）にAzure ADのアプリへアクセスさせたい → Azure AD B2B
  • 招待されたゲストユーザーが自社のAzure ADテナントにアクセス。
  • B2C（一般消費者向けID管理）と混同しない。
B2B vs B2C
B2B = 企業間コラボ（パートナー、取引先）
B2C = エンドユーザー向けアプリのID管理（Googleログイン等のソーシャルID連携）
ガバナンス
全サブスクリプションに一律ルールを強制したい（例：特定リージョンのみ許可） → Azure Policy 頻出！
  • 準拠していないリソースを検出・拒否・自動修復できる。
  • 管理グループに割り当てて組織全体に適用するのが典型パターン。
  • イニシアチブ（Initiative）＝複数ポリシーをまとめたセット。
RBAC と混同注意：RBACは「誰が何をできるか」、Policyは「何を作れるか」のルール。
複数サブスクリプションを階層管理したい → 管理グループ（Management Groups） 頻出！
  • 最大6階層（ルート管理グループ含む）。
  • Azure Policy・RBAC を管理グループに割り当てると配下のサブスクリプションに継承される。
  • 大企業の組織構造（部門別サブスク）をそのまま反映できる。
リソースの誤削除・誤変更を防ぎたい → リソースロック（Resource Locks）
  • CanNotDelete：削除不可・変更は可。
  • ReadOnly：削除・変更ともに不可（= 読み取り専用）。
  • 所有者でもロック解除しなければ削除できない。
コストタグ付け・リソースのグループ化・テンプレートデプロイを一括管理したい → Azure Blueprints / Landing Zone
  • Blueprints = Policy・RBAC・ARMテンプレートを1パッケージにして繰り返しデプロイ。
  • Landing Zone = 大規模組織向けの推奨アーキテクチャパターン（CAF準拠）。
監視・セキュリティ
全リソースのログ・メトリクスを一元監視したい → Azure Monitor 頻出！
  • メトリクス（数値）＋ログ（Log Analytics）の両方を扱う統合監視サービス。
  • アラート → アクショングループ（メール/SMS/Webhook/Functionなど）で自動対応。
  • Application Insights はアプリ専用の監視機能で、Monitorの一部。
Azureリソースの設定ミス・セキュリティリスクを継続的に評価したい → Microsoft Defender for Cloud（旧 Security Center） 頻出！
  • セキュアスコアで現状の姿勢を数値化し、推奨アクションを提示。
  • Defender プラン（有料）を有効にするとVM・SQL・コンテナなどへの脅威検出も可能。
  • マルチクラウド（AWS・GCP）のリソースも監視対象にできる。
Azure全体のセキュリティインシデントをSIEMで管理したい → Microsoft Sentinel
  • クラウドネイティブSIEM/SOAR。Log Analyticsワークスペース上に構築。
  • AIで脅威を検出し、プレイブック（Logic Apps）で自動対応。
シークレット・証明書・暗号化キーを安全に管理したい → Azure Key Vault 頻出！
  • Secrets（接続文字列等）・Keys（暗号化キー）・Certificates を一元管理。
  • HSM（ハードウェアセキュリティモジュール）バックアップオプションあり（Premium SKU）。
  • マネージドIDと組み合わせてコードにシークレットを書かないのが正解パターン。
特権アカウント（全体管理者等）へのアクセスをジャストインタイムで制御したい → Azure AD PIM（Privileged Identity Management） 頻出！
  • 通常は権限なし → 必要なときだけ一時的に昇格（承認フロー付き）。
  • 利用にはAzure AD Premium P2が必要。
  • アクセスレビューで定期的に権限の棚卸しも可能。
② データストレージ
リレーショナルDB
フルマネージドなSQL Server（PaaS）が必要 → Azure SQL Database 頻出！
  • OS・パッチ・バックアップはMicrosoftが管理。SLA 99.99%。
  • DTU モデル / vCore モデルの2種類の購入方式。
  • Hyperscale：最大100TB、読み取りスケールアウト対応の大規模向けサービス。
  • サーバーレス：アイドル時は自動一時停止でコスト削減。
SQL DB vs SQL Managed Instance vs SQL Server on VM
SQL DB = 完全PaaS（一部機能制限あり）
SQL MI = SQL Serverとほぼ100%互換。リフト＆シフト移行向け
SQL on VM = 完全コントロール必要・特殊拡張機能が必要な場合
オンプレのSQL ServerをなるべくそのままAzureに移行したい → Azure SQL Managed Instance 頻出！
  • SQL Agentジョブ・CLR・リンクサーバー・Service Brokerなど、SQL DBでは使えない機能が使える。
  • VNet内にデプロイされるため、既存オンプレシステムとの統合が容易。
  • Database Migration Service（DMS）でオンラインマイグレーション可能。
フルマネージドなMySQL / PostgreSQL / MariaDB が必要 → Azure Database for MySQL / PostgreSQL / MariaDB
  • OSS系DBのフルマネージドPaaS。バックアップ・HA・パッチ自動化。
  • Flexible Server が現在の推奨SKU（Single Serverは非推奨化方向）。
NoSQL / グローバル分散DB
グローバル分散・低レイテンシ・マルチモデルのNoSQLが必要 → Azure Cosmos DB 頻出！
  • マルチリージョン書き込み対応。SLA 99.999%（マルチリージョン時）。
  • API選択肢：NoSQL（SQL構文）/ MongoDB / Cassandra / Gremlin（グラフ）/ Table。
  • 整合性レベル5段階：Strong / Bounded Staleness / Session / Consistent Prefix / Eventual。
  • RU（Request Unit）課金：1RU = 1KBドキュメントの読み取りコスト。
整合性レベルの選択は頻出。「最高の一貫性=Strong」「最高のパフォーマンス=Eventual」。
ストレージ（Blob・File・Queue・Table）
大量の非構造化データ（画像・動画・バックアップ）を安価に保存したい → Azure Blob Storage 頻出！
  • アクセス層：Hot（頻繁）/ Cool（30日以上）/ Cold（90日以上）/ Archive（180日以上、取り出しに時間がかかる）。
  • ライフサイクル管理ポリシーで自動的に層を移動・削除できる。
  • 不変ストレージ（WORM）：法規制対応・改ざん防止。
  • Data Lake Storage Gen2：Blob + 階層型名前空間（ビッグデータ分析向け）。
アクセス層の選択基準
Hot = 毎日アクセス / Cool = 月に数回 / Archive = 年に1回程度・監査保存
SMB/NFSのファイル共有をクラウドで使いたい（オンプレのファイルサーバー移行） → Azure Files 頻出！
  • SMB 3.0 / NFS 4.1 対応。Windowsドライブとしてマウント可能。
  • Azure File Sync：オンプレのファイルサーバーとクラウドをリアルタイム同期。キャッシュ機能付き。
  • Premium（SSD）/ Standard（HDD）の2ティア。
「オンプレのファイルサーバーをクラウド化したい」→ Azure Files + File Sync が鉄板。
アプリ間のメッセージキューが必要（簡易・大量） → Azure Queue Storage（簡易） / Azure Service Bus（高機能）
Queue Storage vs Service Bus
Queue Storage = シンプル・大量メッセージ（最大64KB/件、最大80GB）
Service Bus = 順序保証・重複排除・セッション・Dead Letter Queue（DLQ）など高機能
「メッセージの順序保証が必要」「1件256KBを超えたい」→ Service Bus を選ぶ。
キャッシュ・検索
DBへのクエリ負荷を減らしたい / セッション管理をしたい → Azure Cache for Redis 頻出！
  • インメモリキャッシュ。Read-through / Write-behind パターンで利用。
  • セッション状態の外部化（スケールアウト時に有効）。
  • リーダーボード・Pub/Sub にも使われる。
全文検索・AI検索機能をアプリに組み込みたい → Azure AI Search（旧 Cognitive Search）
  • Blobやデータベースからインデクサーでデータを取り込み、全文検索を提供。
  • AI Enrichment：OCR・言語検出・エンティティ抽出を組み合わせ可能。
  • ベクター検索（RAGパターン）にも対応。
③ 事業継続性（DR・バックアップ・HA）
重要指標（必ず暗記）
RTO / RPO の定義 → RTO = 復旧時間目標　／　RPO = 復旧時点目標 頻出！
  • RTO（Recovery Time Objective）：障害発生からサービス復旧までの最大許容時間。
  • RPO（Recovery Point Objective）：障害発生時に許容できる最大データ損失時間。
判断の基準
RTO短い = サービス止められない → 自動フェールオーバー必須
RPO短い = データ損失NG → 同期レプリケーション or 高頻度バックアップ
「RTO=0, RPO=0」の要件 → Active-Active 構成（Azure Traffic Manager + 複数リージョン）。
バックアップ
VM・SQL・Blob・ファイルの一元バックアップ管理をしたい → Azure Backup 頻出！
  • Recovery Services Vault にバックアップデータを保管。
  • オンプレ（MARS エージェント）からもバックアップ可能。
  • 論理的削除（Soft Delete）：誤削除から14日間保護。
  • Backup Center でマルチサブスクリプションのバックアップを一元管理。
ディザスタリカバリ（DR）
VMやオンプレサーバーのDRを自動化したい → Azure Site Recovery（ASR） 頻出！
  • Azure → Azure / オンプレ → Azure / Azure → オンプレ のレプリケーションが可能。
  • フェールオーバーテストを本番に影響なく実施できる。
  • RPO は数秒〜数分、RTOは数分〜数時間（ポリシー次第）。
高可用性（HA）パターン
同一リージョン内でVMの冗長性を確保したい → 可用性セット（Availability Set）/ 可用性ゾーン（Availability Zones） 頻出！
可用性セット vs 可用性ゾーン
可用性セット = 同一DC内で障害ドメイン・更新ドメインに分散。SLA 99.95%
可用性ゾーン = 異なる物理DC（ゾーン）に分散。SLA 99.99%。より高い冗長性。
「99.99%のSLAが必要」→ 可用性ゾーンを選ぶ。
マルチリージョンで自動フェールオーバーしたい → Azure Traffic Manager + 複数リージョン構成 頻出！
  • Traffic Manager は DNS ベースのグローバルロードバランサー（L7ではなくDNS）。
  • ルーティング方式：Priority（優先度）/ Weighted（重み）/ Performance（最低レイテンシ）/ Geographic。
  • 障害検出（ヘルスチェック）に基づいて自動的にDNSを切り替え。
「グローバルDR」= Traffic Manager。「リージョン内HA」= Load Balancer / App Gateway。
Azure SQL Databaseのマルチリージョン DR を設定したい → アクティブ geo レプリケーション / フェールオーバーグループ
  • アクティブ geo レプリケーション：最大4つのセカンダリDB（読み取り可能）を別リージョンに作成。
  • フェールオーバーグループ：接続文字列を変えずに自動フェールオーバー。複数DBをまとめて管理。
④ インフラ（コンピューティング・ネットワーク）
コンピューティング選択
どのコンピューティングサービスを選ぶか → 用途別の選択ガイド 頻出！
サービス選ぶ場面
Azure VMIaaS・フル制御・レガシーアプリ移行
Azure App ServiceWeb/API アプリ。PaaS。OS管理不要
Azure Kubernetes Service（AKS）コンテナオーケストレーション・マイクロサービス
Azure Container Instances（ACI）単発・シンプルなコンテナ実行（オーケストレーション不要）
Azure Functionsイベント駆動・サーバーレス・短時間処理
Azure Logic Appsワークフロー自動化・ノーコード統合
Azure Batch大規模並列バッチ処理（HPC）
VMのコストを最小化したい（中断可能なワークロード） → Azure Spot VM
  • 通常価格比最大90%割引。ただしAzure側の都合で強制停止（立ち退き）される場合あり。
  • バッチ処理・レンダリング・テスト環境など中断を許容できるワークロード向け。
コスト削減オプション比較
Reserved VM（予約）= 1〜3年コミットで最大72%割引。停止は自由
Spot VM = 最大90%割引。ただし強制停止リスクあり
Azure Hybrid Benefit = 既存のWindowsServer/SQLライセンスをAzureで利用
ネットワーク
ロードバランサーの選択 → 用途別の選択ガイド 頻出！
サービスレイヤースコープ特徴
Azure Load BalancerL4（TCP/UDP）リージョン内シンプル・高パフォーマンス。非HTTP含む
Application GatewayL7（HTTP/S）リージョン内WAF・SSL終端・URLルーティング・Cookie セッション
Azure Front DoorL7（HTTP/S）グローバルグローバルCDN＋LB＋WAF。Anycastで最寄りPoPへ誘導
Traffic ManagerDNSグローバルDNSベース。HTTP以外も対応。フェールオーバー・地理分散
「WAF付きグローバルLB」→ Azure Front Door。「WAF付きリージョンLB」→ Application Gateway。
オンプレとAzureを安全に接続したい → VPN Gateway（インターネット経由）/ ExpressRoute（専用線） 頻出！
VPN Gateway vs ExpressRoute
VPN Gateway = インターネット経由の暗号化トンネル（IPsec）。安価・導入容易
ExpressRoute = 専用閉域網（キャリア経由）。高帯域・低レイテンシ・SLA保証
「高帯域・低レイテンシ・セキュアな専用接続が必要」→ ExpressRoute が正解。
複数のVNetをハブ&スポーク構成でセキュアに接続したい → Azure Virtual WAN / VNet Peering + ハブVNet
  • VNet Peering：低レイテンシのVNet間接続（同一リージョン / クロスリージョン対応）。推移的ルーティングは不可。
  • Virtual WAN：大規模なハブ&スポークをマネージドで管理。推移的ルーティングが可能。
  • Azure Firewall：ハブVNetに配置してEast-West / North-South トラフィックを検査。
AzureサービスへのアクセスをVNet内に閉じたい（パブリックIP不要） → プライベートエンドポイント（Private Endpoint） 頻出！
  • Blob・SQL・Key Vaultなどに対してVNet内のプライベートIPアドレスを割り当てる。
  • インターネットを経由せずにAzureサービスへアクセス可能。
Private Endpoint vs Service Endpoint
Private Endpoint = VNet内にプライベートIPを作成。より強固な分離
Service Endpoint = VNetからAzureサービスへの経路最適化。パブリックIPは残る
Webアプリを外部アクセスなしにVNet内から安全に公開したい → App Service + VNet統合 / App Service Environment（ASE）
  • VNet統合：App ServiceからVNet内のリソースへのアウトバウンド接続を有効化。
  • Private Endpoint for App Service：App ServiceへのインバウンドをVNet内に限定。
  • ASE（App Service Environment）：完全にVNet内に配置する専用環境（高コスト・高セキュリティ）。
⑤ アプリケーションアーキテクチャ
メッセージング・統合
メッセージングサービスの選択 → 用途別の選択ガイド 頻出！
サービス選ぶ場面
Azure Service Bus信頼性の高いメッセージキュー。順序保証・DLQ・セッション・重複排除
Azure Event Hubs大量のイベントストリーム取り込み（IoT・ログ・テレメトリ）。Kafka互換
Azure Event Gridイベント駆動アーキテクチャ。リソース変更などのイベントをFunctionやLogic Appsに転送
Azure Queue Storageシンプルで大量のキュー（64KB/件まで）
「大量データの取り込み・ストリーム処理」→ Event Hubs。「信頼性の高いメッセージ」→ Service Bus。「イベント通知」→ Event Grid。
サービス間の疎結合・イベント駆動アーキテクチャを実現したい → Azure Event Grid
  • パブリッシャー（Blob作成・リソース変更等）→ Event Grid → サブスクライバー（Function・Logic Apps・Webhook）。
  • プッシュ型（サブスクライバーにイベントを配信）。ポーリング不要。
  • カスタムトピックを作成して独自イベントも発行できる。
API管理・統合
複数のバックエンドAPIを一元管理・保護・監視したい → Azure API Management（APIM） 頻出！
  • APIゲートウェイ：レート制限・認証・キャッシュ・変換をポリシーで設定。
  • 開発者ポータルで APIドキュメント・テスト環境を自動公開。
  • バックエンドはAzure FunctionでもオンプレAPIでも可。
サーバーレス・自動化
イベントに応じて短時間のコードを実行したい（サーバーレス） → Azure Functions 頻出！
  • トリガー：HTTP / Timer / Blob / Queue / Event Hub / Service Bus / Event Grid など多数。
  • 消費プラン（サーバーレス）：実行回数・時間で課金。自動スケール。
  • Durable Functions：複数ステップのワークフローをオーケストレーション。
Functions vs Logic Apps
Functions = コード（C#/Python/JS等）で記述。開発者向け
Logic Apps = GUIでワークフローを組み立て。300以上のコネクタ。ノーコード向け
CDN・静的コンテンツ配信
静的コンテンツをグローバルに高速配信したい → Azure CDN / Azure Front Door
  • Azure CDN：コンテンツをエッジにキャッシュ。Blob Storageと統合が簡単。
  • Azure Front Door：CDN＋グローバルLB＋WAF＋ヘルスチェック。Webアプリ全体を対象。
「Webアプリのグローバル加速＋WAF」→ Front Door。「静的ファイルのキャッシュだけ」→ CDN。
マイクロサービス・コンテナ
マイクロサービスの分散アプリケーションを構築したい → Azure Kubernetes Service（AKS） / Azure Container Apps 頻出！
AKS vs Container Apps vs ACI
AKS = フル制御のK8s。複雑だが柔軟性最高
Container Apps = マネージドK8s（制御は少ない）。KEDA/Daprが統合済み。マイクロサービス向け
ACI = 単一コンテナを素早く起動するだけ。オーケストレーション不要な場合
アーキテクチャパターン
大量の同時リクエストでもスケールするWebアプリを設計したい → ステートレス設計 + 水平スケール + キャッシュ
  • セッション状態をRedisに外部化（ステートレス化）→ App Serviceのインスタンスを自由にスケール。
  • CDN で静的コンテンツをキャッシュ → オリジンへの負荷軽減。
  • 読み取り負荷 → Cache-Aside パターン（キャッシュになければDBから取得してキャッシュに書く）。
レガシーモノリスをクラウドネイティブに段階的移行したい → Strangler Fig パターン
  • 既存システムを残しながら、機能を少しずつマイクロサービスに切り出す。
  • Azure API ManagementやAzure Front Doorをファサードとして置き、背後のルーティングを切り替えながら移行。
